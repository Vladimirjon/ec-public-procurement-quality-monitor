- `WINDOWS_RESERVED_NAMES` is `con`, `prn`, `aux`, `nul`, `com0` to `com9` and `lpt0` to `lpt9`, lowercase.
- `IngestScope` construction raises `ValueError` (naming the field, never its value) when:
  - `base_url` or `buyer` is not a non-empty `str`;
  - `year`, `first_page` or `last_page` is not an `int` (a `bool` is rejected) of at least 1;
  - `first_page > last_page`.
- `to_json()` returns exactly `{"scope_version": 1, "source": "sercop-search-ocds", "base_url", "buyer", "year", "first_page", "last_page"}` (intent AC13, Q6).
- `from_json` accepts only a mapping with exactly those seven keys, `scope_version` the `int` 1 and `source` that string, and raises `ValueError` otherwise. A resumption uses it to read its original's scope (AC24 "malformed").
- `validate_ingest_execution_id` returns the id when it matches `ingest-[0-9]{8}t[0-9]{6}z-[0-9a-f]{8}` (32 characters), passes F1's `validate_execution_id`, and is not in `WINDOWS_RESERVED_NAMES`; otherwise `ValueError`.
- `pages_left_to_request(scope: IngestScope, completed: frozenset[int], last_reached: int | None) -> tuple[int, ...]` returns, in increasing order, the pages of `[scope.first_page, scope.last_page]` that are not in `completed` and are not above `last_reached`. `last_reached` is the `page` of the chain's one valid `last-page-reached` event (§ State machine H, step 3), or `None` when the chain has none. An event that fails that validation is never passed here: it makes the chain malformed. § State machine H uses it to compute the resumption's pages and to validate every `first_page` (decision P-4).

- `RepositoryOpener()` raises `PersistenceConnectionError` when the database cannot be reached.
- The use case passes `IngestReporter.progress` only text it built from fixed words, integers, content hashes, execution ids and `str()` of a project error (F1, F2 and F3 messages are fixed text). For any other exception it passes only `type(error).__name__`.
- **Required progress** (intent AC6 c, AC15, Q9; Revision 6, audit finding F-07). The wording is free; the content of these lines is required, and `run_ingest` calls `progress` at least for:
  1. each page that State machine P processes: one line naming the page and, when a response was stored, its sequence, status and content hash; a page with no response is named with fixed words for that (for example `page 2 no response`);
  2. each database operation, read or write, refused by a `PersistenceError` that is not a connection loss, **in any phase of `run_ingest`** (Revision 7, audit findings F-13 and F-14): the openings of a repository, the ingest exclusion, § State machine T, R, H and I, `start_run`, P step 4, § State machine P "Refused writes", the repeats, re-checks, second opening and second exclusion of § State machine C, the `read_run` after a refused P-2 repeat (C step 5), and every operation of § State machine K;
  3. each `PersistenceConnectionError` (a lost connection), **in the same phases**, and a `PersistenceConnectionError` from `open_repository()` (the first opening, and the second one of § State machine C). Revision 6 required these lines only "from `start_run` on"; intent AC15 requires them for every lost operation, and Revision 7 follows AC15 (intent § Risks, P-2: stderr still reports the lost connection).

  Rules shared by items 2 and 3 (required):
  - *Database operation* means a call of `open_repository()` or of an `IngestionRepository` operation (`try_acquire_ingest_exclusion`, `read_run`, `list_runs`, `list_observations`, `list_audit_events`, `start_run`, `record_observation`, `append_audit_event`, `finish_run`).
  - Exactly one line per failed call: a call that fails once gives one line, and its repeat under § State machine C, if it fails too, gives its own line.

### Output (intent AC15)
- stdout:
  - exactly one line `<execution_id> <status>` when the outcome names a run, whatever the exit code, where `<status>` is the outcome's `run_status` value (`succeeded`, `failed` or `running`);
  - `<status>` is the last status this process confirmed for its run. `running` means that closing was not confirmed, not a claim that PostgreSQL still holds `running` (decision P-5);
  - nothing otherwise;
  - when any exception (a `KeyboardInterrupt` or any other) escapes `run_ingest` after `reporter.run_started(id)` was called, the line is `<id> running`, even if a `finish_run` may have committed unseen (decision P-5; extended from `KeyboardInterrupt` to every escaping exception in Revision 6, audit finding F-04); the exit code is 130 for a `KeyboardInterrupt` and 1 otherwise;
  - after the P-2 case of § State machine C, the line is `<id> succeeded` with exit 0;
  - at most one line per invocation, whatever happens after it is written: a `KeyboardInterrupt` while the source is closed (invocation step 7) adds no second line (Revision 7, audit finding F-16);
  - closing the final repository never changes the line: an `Exception` from that close is suppressed inside `run_ingest`, and a `KeyboardInterrupt` during it gives `INTERRUPTED` (exit 130) with the status already confirmed, so a run whose closing was confirmed prints `<id> succeeded` or `<id> failed`, never `<id> running` (Revision 9, audit finding F-22; § Public names, "The final close").
- **Writing the result** (Revision 10, sweep finding N-7; required). The command writes its result at invocation step 6: after `run_ingest` returned, the final stderr message (`IngestOutcome.message`) and, when the outcome names a run, the result line with the outcome's `run_status`; after an exception escaped `run_ingest`, the handler's `<id> running` (when the run was announced) and its stderr line (`interrupted`, or `unexpected error: <class>`). A `KeyboardInterrupt` or any other exception (`MemoryError` included) raised while it writes any of these, by the stream or by a Ctrl+C, is handled by these rules:
  - *The confirmed status is kept.* Once `run_ingest` returned an outcome, the only result line the command attempts is the outcome's. An exception while it writes the final message or the result line never leads to `<id> running` or to any other status. In particular, a run confirmed `succeeded` never prints `<id> running` because writing failed. A failure while the final stderr message is written does not prevent the one attempt of the result line. The order of the two writes is free.
  - *At most one attempt.* The result line is attempted at most once per invocation. Once the command has started to write a result line (the outcome's line or a handler's `<id> running`), no other result line is attempted, whatever is raised afterwards, including a raise from the line end that follows the text. This extends F-16 (b).
  - *Exit code* (decided by the human on 2026-10-20, amending the architect's draft). A `KeyboardInterrupt` raised while the command writes gives exit 130. Any other exception (`OSError`, `MemoryError`, any `Exception`) that prevents writing the final result gives exit 1, unless an interruption had already made the exit code 130, which is kept (for example inside the command's handler for an escaping `KeyboardInterrupt`). In both cases the result line, if one is attempted, keeps the status above, the exception is suppressed, and PostgreSQL is not touched: the run is not read or modified because of it. So a run may stay `succeeded` in PostgreSQL while the command ends with 1 because of an output failure; the operator's evidence is the stored run, and the next `ingest` does not reconcile it (it is not `running`). A Ctrl+C is not swallowed: 130 records it (F-16 b, F-22).
  - *Nothing escapes.* No such exception escapes `run_ingest_command` (except `SystemExit`), so no traceback is printed. This holds also when the exception arrives inside the command's own handler for an exception that escaped `run_ingest`. The command may write a further stderr line about it (`interrupted`, or at most the class name); the failure of that line is suppressed in turn and gets no further line.
  - *Not guaranteed.* A complete line, when the output stream itself fails: the line being written (the result line or a stderr line) may be partial or missing, and nothing is written in its place. This is accepted.
- stderr:
  - `argparse` usage and errors;
  - the configuration message of invocation step 2;
  - the applied migration names;
  - `IngestReporter.progress` lines, at least the required ones of § Public names and signatures (F-07);
  - one final line with `IngestOutcome.message`;
  - for an exception that escapes, only its class name.
- Never on stderr or stdout: a traceback, an exception chain or `__context__` (R-6, raw-evidence N3), a URL, a header value, body bytes, a setting value or the password.

### State machine P: one page (intent AC1 to AC6, AC17)
`next_sequence` starts at 1. Each page `p`, from the run's first page to request up to `scope.last_page`:

1. **Request.** `outcome = source.search_page(year=..., buyer=..., page=p)`. Catch `SourceError` only, and leave the `except` block before anything else (F2 consumer rules). `response = result.response` or `error.response`.
2. **No response** (`SourceTransportError` with `response is None`) -> `page-failed` (sequence `None`, `transport`, status `None`) -> step 7. No sequence is used (intent AC5).
3. **Store locally.** `observation = store.store(execution_id=..., sequence=next_sequence, **fields of response)`:
   - `OSError` or `EvidenceIntegrityError` -> ask `store.read_observation(id, next_sequence)`;
     - found -> `record_observation` of it (step 4, errors as there), then `storage-failed` (`raw-evidence`, sequence) -> step 7;
     - the read-back itself raises `EvidenceNotFoundError`, `OSError` or `EvidenceIntegrityError` -> treat the observation as not recorded: `storage-failed` (`raw-evidence`, page, sequence) -> step 7 (raw-evidence N2, intent AC6 a, b and d). The use case cannot tell whether a file was published and cannot record an observation it cannot read. This is not a claim that nothing was written. Nothing is lost: a resumption requests that page again, and an unreadable or orphan file counts for nothing (RE-9, intent AC9). For example, a regular file at `<root>/observations` makes the read-back raise `NotADirectoryError` (an `OSError`) on Linux and `EvidenceNotFoundError` on Windows; both end here.
     - `KeyboardInterrupt`, `SystemExit` and `MemoryError` from the read-back are not caught by this rule; they keep the handling of § State machine K (SA-11, Q11).
   - Once `store` returns, `next_sequence += 1`.
   - **Pending local observation** (State machine K; Revision 6, audit findings F-01 and F-02): sequence `s` is *pending* from the moment `store` is called for it until `record_observation` of that observation has returned, including its repeat under § State machine C. It stops being pending only when that `record_observation` returns, or when this step has concluded that the observation is not recorded (the failed read-back above). It is still pending while `store` runs, between `store` and `record_observation`, and while `record_observation` is in flight. It also stops being pending when that `record_observation` raises a refusal (a `PersistenceError` that is not a `PersistenceConnectionError`; Revision 10, sweep finding N-4; required). This holds for the record of step 4, for the record of a published observation after the read-back above, and for its repeat on the second repository under § State machine C. The pending period ends at the moment the refusal is raised, before its progress line is written. So a `KeyboardInterrupt`, a `MemoryError` or another exception that lands afterwards, while that line is written, while `storage-failed` is appended, or anywhere later, never makes § State machine K record that observation ("Refused writes" below: a refusal is answered, never retried).
4. **Record in PostgreSQL.** `record_observation(observation)`:
   - `PersistenceConnectionError` -> § State machine C with this operation pending;
   - any other `PersistenceError` -> a progress line naming `record_observation` and the identity (§ Public names and signatures, required progress 2), then `storage-failed` (`postgresql`, sequence) -> step 7.
5. **Decide.**
   - Error with a response -> `page-failed` (sequence, failure, status) -> step 7.
   - Result -> `page-completed` (page, sequence, content hash).
   - Then, if `p >= result.pages` -> `last-page-reached` (page `p`, `result.pages`) and finish `succeeded` (step 6). There is no condition on `scope.last_page` (decision P-3, intent AC3). The order is binding, and § State machine H validates against it: `page-completed` for `p`, then `last-page-reached` for the same `p`, then `finish_run`. This covers:
     - a beyond-the-last-page result (`is_beyond_last_page`, `p > pages`);
     - the reported last page itself (`p == pages`), also when it equals `scope.last_page`;
     - `pages` 0 with scope 1 to 1.

     No further request is sent, so AC17 (at most one request per page per run) is unaffected.
   - Otherwise (`p < result.pages`) go to the next page; after `scope.last_page`, step 6.
6. **End of range.** Once every page has been processed, `finish_run(SUCCEEDED, clock.now())`, keeping that `finished_at` value for any repeat.
7. **Failure path.** `finish_run(FAILED, clock.now())`, keeping that value, then `RUN_FAILED`. No further request is sent (no retries, Q12).

Every `append_audit_event` and `finish_run` above follows § State machine C on `PersistenceConnectionError`.

**Refused writes** (intent AC6 e, AC13; Revision 6, audit finding F-11). A *refusal* is a `PersistenceError` that is not a `PersistenceConnectionError` (`PersistenceIntegrityError`, `PersistenceNotFoundError` or a plain `PersistenceError`). Each refusal writes the required progress line, is never audited as `unexpected-error` and never enters § State machine K. Only catalogue values are used:

| Refused write | Reaction | Outcome |
|---|---|---|
| `start_run` | nothing is written; `reporter.run_started` is not called | `NOT_STARTED`, no run (exit 1) |
| `record_observation` | step 4 | `RUN_FAILED`, `failed` |
| a normal-path append (`run-started`, `page-completed`, `last-page-reached`) | `storage-failed` (`postgresql`, the page, the sequence of the page's observation or `None`) once, then `finish_run(FAILED)` | `RUN_FAILED`, `failed` |
| the final `finish_run(SUCCEEDED)` (step 6, or after `last-page-reached`) | `storage-failed` (`postgresql`, the last page processed, sequence `None`) once, then `finish_run(FAILED)` with a new clock reading | `RUN_FAILED`, `failed` |
| a failure-path append (`page-failed`, `storage-failed`) | no further event; `finish_run(FAILED)` | `RUN_FAILED`, `failed` |
| `finish_run(FAILED)` | nothing more is written; AC10 closes the run at the next `ingest` | `RUN_FAILED`, `running` (closing not confirmed, P-5) |

At most one `storage-failed` (`postgresql`) answers refusals in a run, so a refusal can never start a loop of events.

**A refusal is answered, never retried** (Revision 10, sweep finding N-4; required; it follows F-11). No write that the database refused is attempted again in the same invocation, by any path, § State machine K included:
- a refused `record_observation` ends the pending period of its sequence (P step 3), so K's step 2 never records that observation; K, entered for an exception that lands after the refusal, still runs its steps 1, 3 and 4 on the current repository (they are other writes);
- after a refused `finish_run(FAILED)` nothing more is written to the run by any path: an exception that lands afterwards (for example while the refusal's line is written) does not enter K, and the outcome is `INTERRUPTED` for a `KeyboardInterrupt` and `RUN_FAILED` otherwise, with `run_status=RUNNING` (stdout `<id> running`, exit 130 or 1);
- the refused write keeps its one progress line; a line interrupted while it is written may be missing or incomplete.

Inside § State machine C its own rules apply first (for example a refused repeat of the final `finish_run(SUCCEEDED)`, step 5); a refusal of a write that C makes on its new connection follows this table.

### State machine C: after `PersistenceConnectionError` (intent AC8, Q3; PS-11, persistence Invariant 7)
Before the new run exists (the exclusion, the target check, reconciliation, chain checks, id draw), no new connection is opened: `NOT_STARTED`, exit 1. The lost operation gets the required progress line (§ Public names, required progress 3: the operation and the identity it concerns), and the outcome message is the fixed message of the state machine in which it happened (§ State machine T, R, H and I; Revision 7, audit findings F-14 and F-15), never only an exception's class name.

From `start_run` on, with pending operation `X` and its exact arguments kept:
1. Close the lost repository quietly. From the loss on it is no longer the current repository (see "The current repository" below): the record says so before the loss line is written and before this close. "Quietly" means (Revision 9, audit finding F-21; required): an `Exception` other than `MemoryError` raised by this `close()` is suppressed with no line, and the recovery continues with step 2; a `KeyboardInterrupt` or a `MemoryError` raised by it ends § State machine C in the window, and the final close of `run_ingest` attempts the lost repository once more (§ Public names, "The final close"). If this call already opened its second repository -> stop: the run is left `running`, `RUN_FAILED` with `run_status=RUNNING`.
2. Open the second repository through `open_repository()`. A failure -> left `running`; a `PersistenceError` here gets the required progress line naming `open_repository` (Revision 7). Any other exception here (Revision 8, audit finding F-19): "The current repository" below.
3. `try_acquire_ingest_exclusion()` on the second repository. `False` or an error, of any kind (Revision 8, audit finding F-18) -> close it; the run is not touched (no event, no `finish_run`); left `running`. An `Exception` other than `MemoryError` raised by that `close()` is suppressed and changes nothing; a `KeyboardInterrupt` or a `MemoryError` raised by it ends C in the window with the outcome of that exception (so `INTERRUPTED` for a `KeyboardInterrupt` that lands while the second repository is closed after a `False`), and the final close attempts the second repository once more (Revision 9, audit finding F-21). An error here gets the required progress line naming `try_acquire_ingest_exclusion` (Revision 7; for every kind of error, Revision 8). Only `True` makes the second repository the current one.

**The current repository** (Revision 8, audit findings F-18 and F-19; required). Every write and every read of the run after `start_run` goes through the *current* repository, and a repository is current only while it holds the ingest exclusion: the first repository until an operation on it raises `PersistenceConnectionError`; then no repository at all, until `try_acquire_ingest_exclusion()` on the second repository has returned `True`; then the second repository. The second repository never becomes current before that `True`.

**The explicit record** (Revision 9, audit finding F-21; required; it is how the rule above is kept, and it takes precedence over any routing of exceptions). The run session holds an explicit record of the current repository, whose value is either a repository that holds the ingest exclusion or *none*:
- it becomes *none* as the first action of the handler that catches a `PersistenceConnectionError` raised by an operation on the current repository, before the loss line is written and before step 1; this holds for the first loss and for a further loss on the second repository (step 6), and also before the run exists (where no new connection is opened);
- it becomes the second repository only right after that repository's `try_acquire_ingest_exclusion()` returned `True`;
- a lost repository, and a second repository that does not hold the exclusion, are kept only so that they can be closed; no other operation is ever called on them.

Every step of § State machine K and every read or write of the run requires a current repository, taken from this record when the exception is handled. With none, § State machine K is not entered, whatever the exception (a `KeyboardInterrupt`, a `MemoryError`, a synthetic defect, an error raised by the reporter, anything other than `SystemExit`) and wherever in the window it was raised: while the lost repository is closed, while the loss line is written, while `open_repository()` runs, while `try_acquire_ingest_exclusion()` runs, while a line of step 2 or 3 is written, while the second repository is closed after a `False` or an error, between the `True` and the update of the record, or between any of these. Which call raised, and whether the exception was wrapped or translated on its way, never decides it.

In the window with no current repository (steps 1 to 3):
- nothing reads or writes the run by any path, § State machine K included; no operation is attempted on the lost repository, which may have lost its session and with it the exclusion (PS-11), nor on a second repository that does not hold the exclusion;
- a `KeyboardInterrupt`, a `MemoryError` or any other exception that arrives in the window (anywhere in the list above), like a `PersistenceError` or a `False` at step 2 or 3, ends § State machine C: the run is not touched, § State machine K is not entered, and the second repository, if one was obtained, is closed (when that close is itself interrupted, the final close of `run_ingest` attempts it once more). The only exception that does not end C is an `Exception` other than `MemoryError` raised by a `close()` at step 1 or step 3, which is suppressed;
- the lines: when the exception came from one of the two database operations of the window, exactly one required progress line names it (`open_repository` or `try_acquire_ingest_exclusion`, named alone, § Public names "Required progress"), with at most the exception's class name. When it landed anywhere else in the window (closing a repository, writing a line, between the steps), no further line is written for it. A `False` gets no line, and the closes of steps 1 and 3 are not database operations. A line interrupted while it is written may be missing or incomplete, and nothing is written in its place. No line names an operation that was not attempted (for example `read_run`), so no cleanup line is written;
- after `start_run` returned, the outcome is `INTERRUPTED` for a `KeyboardInterrupt`, and `RUN_FAILED` for a `False`, a `PersistenceError`, a `MemoryError` or any other `Exception`, always with the run's `execution_id` and `run_status=RUNNING` (closing not confirmed, P-5): stdout `<id> running`, exit 130 for Ctrl+C and 1 otherwise. AC10 closes the run at the next `ingest`;
- while `start_run` itself is the pending operation, the earlier rules give the outcome, unchanged: a `False` or a `PersistenceError` gives `RUN_FAILED` with `run_status=RUNNING` (stdout `<id> running`); a `KeyboardInterrupt` gives `INTERRUPTED` with no run (§ State machine K, "Before `start_run` returned"); any other `Exception` gives `NOT_STARTED` with no run and a message that is at most the class name. Nothing is written in any of them, and the line rule above applies;
- `SystemExit` propagates, and the second repository is still closed (§ Public names: `run_ingest` closes every repository it opened).
- **Two or more exceptions** (Revision 10, sweep finding N-3; required). More than one exception may arrive in the window, or in the closes that follow it: the closes of steps 1 and 3, and the final close's attempt once more of a repository whose close there was interrupted. Then precedence decides the outcome, whatever the order of arrival:
  - a `KeyboardInterrupt` among them gives the `KeyboardInterrupt` outcome: `INTERRUPTED`, exit 130, with the run and `run_status=RUNNING` after `start_run` returned, or with no run while `start_run` is pending;
  - otherwise, any other exception that ends C (a `MemoryError`, a defect) gives its outcome: `RUN_FAILED` with `run_status=RUNNING` after `start_run` returned, or `NOT_STARTED` with no run while `start_run` is pending, exit 1. It also prevails over a `False` or a `PersistenceError` of step 2 or 3, as step 3 already says for its close;
  - an `Exception` other than `MemoryError` from a close stays suppressed and takes no part.

  In every case nothing is read or written, § State machine K is not entered, and the lines are those of the database operation that raised (none for a close). This agrees with "The final close" (F-22): a `KeyboardInterrupt` there turns the determined outcome into `INTERRUPTED`, and an `Exception` there is suppressed.

A `KeyboardInterrupt` that lands after the `True` and before the second repository was made current is in the window too: nothing is written and the second repository is closed. Writing nothing is always safe; writing without the exclusion never is (Q4).
4. Resolve `X`:

   | `X` | Safe to repeat | Resolution |
   |---|---|---|
   | `start_run`, `record_observation`, `finish_run` | yes | repeat with the same values (same scope and `started_at`; same `Observation`; same status and `finished_at`) |
   | `read_run`, `read_observation`, `list_*` | yes (reads) | repeat |
   | `append_audit_event(type, detail, occurred_at)` | **no** | `list_audit_events(id)`; if an event with the same type, a `same_json` detail and the same `occurred_at` instant exists, treat it as stored; otherwise append once |

5. Continue the path that was interrupted:
   - on the normal path (P steps 1 to 6, or the opening `start_run` and `run-started`), append `storage-failed` (`postgresql`, page, sequence or `None`), then `finish_run(FAILED)`;
   - on a failure path, complete that path.
   - Exception (decision P-2, intent AC8): if `X` was the final `finish_run(SUCCEEDED)`, it is repeated with the same `finished_at`. No `storage-failed` is appended and no `finish_run(FAILED)` is attempted.
     - When the repeat returns the run with status `succeeded` and that `finished_at`, the run is **confirmed** `succeeded`: `SUCCEEDED`, exit 0. This holds whether the first attempt had committed or not: F3 returns the stored run for a repeat with the same status and instant, finishes a still-`running` run, and raises `PersistenceIntegrityError` for anything else (PS-7).
     - Confirmation is that successful repeat only. A separate `read_run` is not used: it would add a second path that still needs the repeat when the run is `running`.
     - A `PersistenceIntegrityError` from the repeat, which cannot happen under the exclusion, means `RUN_FAILED` with `run_status` from the stored run (exit 1). The refused repeat gets the required progress line (`finish_run` `succeeded`, the run). When the `read_run` that reads the stored run is itself refused or lost, it gets its own required progress line (`read_run`, the run; Revision 7, audit finding F-13), nothing more is written, no third connection is opened, and the outcome is `RUN_FAILED` with `run_status=RUNNING`.
     - If step 2 or 3 failed, or C ended earlier, the repeat is never made: left `running`, exit 1. The exit code is 130 when a Ctrl+C ended C anywhere in the window: at step 2 or 3 ("The current repository" above, Revision 8), and also while the lost repository was closed at step 1 or while the loss line was written (Revision 10, sweep finding N-8; the window list of "The explicit record").
6. Any further `PersistenceConnectionError` -> left `running`; no third connection. The record becomes *none* again (Revision 9, F-21), so an exception that lands afterwards (for example while the line of the second loss is written) does not enter § State machine K either: `INTERRUPTED` for a `KeyboardInterrupt` and `RUN_FAILED` otherwise, with `run_status=RUNNING`. When the operation lost the second time is the repeat of `start_run` on the second repository, the outcomes of the `start_run` window (the last bullets of "The current repository" above) apply instead (Revision 10, sweep finding N-1; required): the second loss itself gives `RUN_FAILED` with `run_status=RUNNING` (stdout `<id> running`, as a `PersistenceError` there does). A `KeyboardInterrupt` that lands afterwards, before C has determined the outcome (for example while the line of the second loss is written), gives `INTERRUPTED` with no run. Any other `Exception` there gives `NOT_STARTED` with no run and a message that is at most the class name. In the last two, nothing is written, stdout is empty, `reporter.run_started` is not called, and no third connection is opened. Once the outcome is determined, the final close follows § Public names, "The final close".

`started_at`, `finished_at` and `occurred_at` are read from the clock once and reused for every repeat, so that "exactly the same values" holds.

### State machine K: interruption and unexpected exceptions (intent AC7, AC11, AC15, Q11; best effort)
- **Only through the current repository** (Revision 8, audit findings F-18 and F-19; required; it takes precedence over "the same steps 1 to 4" below). The cleanup runs only on the current repository of § State machine C, which is one that holds the ingest exclusion. When the `KeyboardInterrupt` or the other exception arrives while there is no current repository (C steps 1 to 3, after a lost connection and before the second repository's exclusion returned `True`), the cleanup does not run: no step below is taken, nothing is read from or written to the run, and § State machine C, "The current repository", gives the lines and the outcome (`INTERRUPTED` or `RUN_FAILED`, `run_status=RUNNING`). Whether a current repository exists is read from the explicit record of § State machine C when the exception is handled (Revision 9, audit finding F-21): with none, K is not entered, whatever the exception and wherever in the window it was raised, and no line names an operation of K.
- `KeyboardInterrupt` raised inside the run, after `start_run` returned. The cleanup, in this order:
  1. **Is the run still open?** (Revision 6, audit finding F-05, intent AC11.) `read_run(id)` on the current repository. If the run is `succeeded` or `failed` (the interrupted operation was a `finish_run` that had committed), the cleanup writes nothing: no observation, no event, no `finish_run`. It returns `INTERRUPTED` with `run_status` = the stored status. If the run is `running`, continue.
  2. **Pending local observation** (P step 3; F-01, F-02). If a sequence `s` is pending (a refused `record_observation` of `s` already ended its pending period, so a refused record is never attempted again here; Revision 10, sweep finding N-4), ask `store.read_observation(id, s)`:
     - found -> `record_observation` of it;
     - `EvidenceNotFoundError`, `EvidenceIntegrityError` or `OSError` -> nothing was published, or what was published cannot be read: record nothing for `s` and continue with step 3 (the rule of F-3 and intent AC6 d; nothing is lost, because a resumption requests that page again and an orphan or unreadable file counts for nothing).
  3. Append `run-interrupted` (page).
  4. `finish_run(FAILED)`.
  5. Return `INTERRUPTED` with the `run_status` that `finish_run` returned.
- Any other `Exception` that is not a project error (a synthetic transport defect, `MemoryError`), raised inside the run after `start_run` returned, while a current repository exists (first bullet): the same steps 1 to 4, with `unexpected-error` (page, class name) at step 3, returning `RUN_FAILED`. At step 1, a run already finished gives `RUN_FAILED` with the stored status (exit 1).
- What the cleanup tolerates (best effort, Q11):
  - It opens no new connection (no § State machine C), and it never uses a repository that is not the current one (first bullet).
  - The three read-back errors of step 2 are the only exceptions it absorbs and continues past.
  - Any other `Exception` raised during the cleanup stops it at once: a `PersistenceError` from `read_run`, `record_observation`, the append or `finish_run`, a `MemoryError`, or anything else. Nothing more is written, and it returns the outcome of its kind (`INTERRUPTED` or `RUN_FAILED`) with `run_status=RUNNING` (closing not confirmed, P-5). In particular, when `read_run` itself fails, nothing is written, because the cleanup cannot show that the run is still open (AC11); AC10 closes the run at the next `ingest`.
  - **Progress line** (Revision 7, audit finding F-13; required progress 2 and 3): whenever one of the cleanup's own database operations, the step 1 `read_run`, the step 2 `record_observation` of the pending observation, the step 3 append (`run-interrupted` or `unexpected-error`) or the step 4 `finish_run(FAILED)`, raises an `Exception` (refused, lost, or anything else), the cleanup writes exactly one `reporter.progress` line before it stops: fixed words, the operation (with the event type for the append, the sequence `s` for the record, `failed` for `finish_run`), the run's execution id, and at most the exception's class name. Then it returns as above. The three read-back errors of step 2 come from the store, not the database, and need no line. A `KeyboardInterrupt` during the cleanup propagates without a required line.
  - **Any `KeyboardInterrupt` raised during the cleanup propagates out of `run_ingest`** (Revision 10, sweep finding N-2; required), whether the cleanup was entered for a `KeyboardInterrupt` (a second one) or for a `MemoryError` or another unexpected exception, and wherever in the cleanup it lands, including after the step 1 `read_run` returned and while the cleanup writes the line of a failed operation. `SystemExit` propagates too. The final close is still attempted (§ Public names, "The final close", last bullet), and the command treats the interrupt as any escaping `KeyboardInterrupt` (invocation step 6): exit 130, stdout `<id> running` (closing not confirmed, P-5), stderr `interrupted`, no traceback. Chosen because it is the approved behavior of a second Ctrl+C during the cleanup (AC7, the `interrupt` row) and of P-5, and the code already behaves this way for both kinds of cleanup. F-05, F-16 (b) and F-22 keep a status only when it was already confirmed and nothing was in flight; during K a write may be in flight, so `running` is the honest line.
- Before `start_run` returned, there is nothing to clean: `INTERRUPTED` with no run. If `start_run` committed unseen, AC10 closes the run later.
- A database refusal never reaches this machine as an "unexpected" error: a `PersistenceError` raised by a write of P is handled by P step 4, § Refused writes or § State machine C, and is never audited as `unexpected-error` (F-11). After a refused `finish_run(FAILED)` the cleanup does not run at all, and a refused `record_observation` is never recorded by step 2 (§ State machine P, "A refusal is answered, never retried"; Revision 10, sweep finding N-4).
- `SystemExit` is never caught.

### State machine T: resumption target (intent AC9, AC14; finding 22)
`read_run(target)` gives one of:
- `PersistenceNotFoundError` -> `INVALID_TARGET`;
- `SUCCEEDED` -> `INVALID_TARGET`;
- `RUNNING` or `FAILED` -> continue;
- any other `PersistenceError`, a refusal or a `PersistenceConnectionError` (Revision 7, audit finding F-15) -> `NOT_STARTED`, never `INVALID_TARGET` (exit 1, not 2: the target's existence is unknown), no new connection, the required progress line (`read_run`, the target id), and a fixed outcome message naming the target id that does not call it invalid (suggested: `the resumption target <id> could not be read`).

Nothing is written in this step.

### State machine R: reconciliation (intent AC10, Q4, Q14)
For each run `X` in `list_runs(RUNNING)` (in its order), while the exclusion is held:
1. `local = store.list_observation_sequences(X)`; `EvidenceIntegrityError` or any `OSError` -> problem `local-listing-failed` (sequence `None`).
2. `pg = {o.sequence: o for o in repository.list_observations(X)}`.
3. For each sequence in `sorted(set(local) | set(pg))`, the first problem found ends the step:
   - in `pg` but not `local` -> `local-observation-missing`;
   - `store.read_observation(X, s)` raises `EvidenceIntegrityError`, `EvidenceNotFoundError` (the file was listed and vanished before it was read) or any `OSError` (for example `PermissionError`) -> `local-observation-unreadable` (Revision 6, audit finding F-10);
   - in `pg` and different from it -> `local-observation-different`;
   - `store.read_content(o.content_hash)` raises `EvidenceNotFoundError` -> `object-missing`; `EvidenceIntegrityError` or any `OSError` -> `object-integrity` (the object cannot be shown to match its hash; Revision 6, F-10).
4. After every listed sequence is verified, the union must be exactly `1..max`; the smallest missing number (or a `0`) -> `sequence-gap` with that sequence. A later observation is verified before the gap is reported (intent AC10).
5. For each local-only sequence, in order: `record_observation(o)`; a refusal (`PersistenceIntegrityError`, or any other `PersistenceError` that is not a connection loss) -> `postgresql-observation-conflict`; then `observation-reconciled` (sequence).
6. `run-closed-by-reconciliation` (count of step 5), then `finish_run(X, FAILED, clock.now())`.

On a problem: `reconciliation-failed` (sequence, problem), `finish_run(X, FAILED)`, `NOT_STARTED`. Runs not yet examined stay `running` for the next invocation. Orphan objects are never looked for. A `PersistenceConnectionError` here (from `list_runs`, `list_observations(X)`, a `record_observation` of `X`, an append to `X` or `finish_run(X, FAILED)`) -> `NOT_STARTED`, with no new connection; nothing more is written to `X`, which may stay `running` for the next invocation; the required progress line names the lost operation and `X` (`list_runs` is named alone); and the outcome message is the same fixed message as a refusal below, naming `X` (or saying that the running runs could not be listed), never only an exception's class name (Revision 7, audit findings F-14 and F-15).

The closed list of Q6 is not extended (F-10): an `OSError` or a vanished file is always mapped to the closest value above, so it never escapes the reconciliation: it is recorded as `reconciliation-failed` and `X` is finished `failed`, with exit 1 and no new run, unless that write itself is refused or lost (next sentence and the connection rule above). A refusal (F-11) of `list_runs` or `list_observations`, of an append (`observation-reconciled`, `run-closed-by-reconciliation`, `reconciliation-failed`) or of `finish_run(X, FAILED)` -> nothing more is written to `X`, the required progress line names the operation and `X`, and the outcome is `NOT_STARTED` with a message naming `X`; `X` may stay `running` for the next invocation.

### State machine H: resumption chain (intent AC9, AC24, Q13, Q14)
1. Starting at the target, follow `run-started.resumes` to a run whose `resumes` is `None`. For each run:
   - not found -> malformed;
   - already visited -> cyclic;
   - not exactly one `run-started` event, or its detail not exactly `{"resumes": str | None, "first_page": int >= 1}` (a `bool` rejected, `resumes` passing `validate_execution_id`) -> malformed;
   - scope not readable by `IngestScope.from_json`, or not `same_json` to the target's scope -> contradictory;
   - a run other than the target that is `succeeded` or `running` -> contradictory.
2. For every `page-completed` event in the chain, the detail must have exactly `page`, `sequence` and `content_hash`, with the page inside the scope range. That run's observation for that sequence must have status 200 and that content hash both in PostgreSQL (`read_observation`) and in the store (`read_observation`); otherwise -> contradictory. A read that fails counts as "otherwise" (Revision 6, audit finding F-06): `PersistenceNotFoundError` from PostgreSQL, and `EvidenceNotFoundError`, `EvidenceIntegrityError` or any `OSError` from the store (a local record that is missing, corrupt or unreadable), each -> contradictory, with the fixed message below.
3. **Validation of `last-page-reached`** (required by the human on 2026-10-15, intent AC24). Event order is the order `list_audit_events` returns (by `event_id`). Before any such event is used as a limit, every one in the chain must pass all of these, or the chain is malformed:
   - its detail has exactly the keys `page` and `pages`, each an `int` that is not a `bool` (floats cannot be stored, PS-10);
   - `scope.first_page <= page <= scope.last_page` (the chain shares one scope, step 1), `pages >= 0` and `page >= pages`;
   - it is the only `last-page-reached` event of its run, and the only one in the whole chain. Two events, in one run or in two, are rejected rather than ranked: no precedence rule exists (confirmed by the human on 2026-10-15), and the consequence below shows none is needed;
   - the same run holds a `page-completed` event for the same `page`, earlier in its event order, that passed step 2. This is the order State machine P writes (P step 5);
   - no `page-completed` and no `page-failed` event of that run comes after it in its event order. Other events may follow it: `run-interrupted`, `unexpected-error`, `storage-failed` (an interrupted or failed close; confirmed by the human on 2026-10-15), and the reconciliation events;
   - **coverage** (required by the human on 2026-10-15): at the point where the event for page `p` is reached, the set `covered` contains every page from `scope.first_page` to `p`. `scope` is the one scope the whole chain shares (step 1, `same_json`), not a run's `run-started.first_page`.
     - `covered` is built in one deterministic walk: runs from the oldest (`resumes` `None`) to the resumed target, and within each run its events in `list_audit_events` order.
     - Each `page-completed` that passed step 2 adds its page. Step 2 is the existing definition of a valid `page-completed`: a page inside `[scope.first_page, scope.last_page]` and the sequence of a `200` observation present in both stores with the same content hash (intent AC1, AC5, Q14).
     - A `page-completed` for a page below `scope.first_page` or above `scope.last_page` never reaches `covered`: step 2 already makes the chain malformed.
     - Any page of `[scope.first_page, p]` missing from `covered` -> malformed.

   **Consequence** (used by steps 4 and 5): after a valid event for page `p`, every page of `[scope.first_page, p]` is in `covered` and no page above `p` is left to request, so nothing is pending. Step 5 then forces every later run of the chain to be a sentinel run (`first_page = last_page + 1`, no page events). A sentinel run holds no `page-completed`, so it cannot hold the preceding `page-completed` that a second valid event needs; and a second event earlier in the chain would make the run that wrote this one a sentinel run too. So two events are never both valid, and a second one is always malformed.

   The event that passes is *the chain's valid `last-page-reached`*; its `page` is the `last_reached` of `pages_left_to_request`. An event that fails never limits anything: the resumption ends `NOT_STARTED` (exit 1) before any request.

   Interaction with reconciliation (§ State machine R): the order is fixed. R runs for every `running` run (invocation step 5.4) before this step (5.5). R reads observations only, never audit events, and appends only `observation-reconciled`, `run-closed-by-reconciliation` or `reconciliation-failed`, none of which is a page event. In particular, R never appends a `page-completed` (Q14: completeness is never decided from stored bytes), so `covered` holds only the `page-completed` events the runs wrote themselves. A run closed by R is validated here like any other, and R can neither create nor repair a `last-page-reached`.

   Interaction with the sentinel (P-4, step 5): a run whose `first_page` is `last_page + 1` holds no page events, so it adds nothing to `covered` and cannot hold a `last-page-reached`. Its own `first_page` is accepted only when step 4, applied to the chain before it, finds nothing left; a valid event earlier in the chain is one way that happens.
4. *Left to request*: a page of `[first_page, last_page]` that no run in the chain completed and that is not above the `page` of the chain's valid `last-page-reached` (step 3; intent AC3 across a chain).
   - The new run requests, in increasing order, every page left to request.
   - Its `run-started` gets `resumes` = target and `first_page` = the smallest page left to request.
   - When none is left, `first_page` is `last_page + 1` (decision P-4): a sentinel valid only for that case. The run then requests nothing and finishes `succeeded`.
5. Validation of every `first_page` already in the chain (decision P-4, intent AC24), applied to each run in step 1, after step 3:
   - a run with `resumes` `None` must have `first_page == scope.first_page`;
   - a run with `resumes` = R must have `first_page` equal to what step 4 computes from the chain that starts at R. That is the smallest page left to request after R's chain, counting R's chain's valid `last-page-reached` if any, or `last_page + 1` exactly when none was left.
   - Any other value is malformed, inside the range or out of it (for example `0`, `last_page + 2`, or `last_page + 1` while a page was still left).
   - A run whose `first_page` is `last_page + 1` must hold no `page-completed` and no `page-failed` event; otherwise it is malformed.

   The same domain function both computes and validates, so the check is pure: `domain/ingestion_catalogue.py` gains `pages_left_to_request(scope: IngestScope, completed: frozenset[int], last_reached: int | None) -> tuple[int, ...]`.

Any failure -> `NOT_STARTED`, with a fixed message naming the execution id; nothing is appended to any run (Q5; reconciliation events already written by R stay). The message holds fixed words and the target execution id (it may also name the run of the chain concerned); it is never only an exception's class name and never `str()` of an exception that is not a project error (intent AC24; F-06).

A database read of this machine (`read_run` of a run of the chain, `list_audit_events`, PostgreSQL `read_observation`) that raises a `PersistenceError` other than `PersistenceNotFoundError`, a refusal or a `PersistenceConnectionError`, is an operational failure, not a verdict on the chain (Revision 7, audit finding F-15): `NOT_STARTED` (exit 1), no new connection, nothing appended to any run, the required progress line (the operation and the run read), and a fixed message that names the target execution id and does not call the chain invalid, malformed, cyclic or contradictory (suggested: `the resumption chain of <id> could not be read`). `PersistenceNotFoundError` keeps the meaning steps 1 and 2 give it.

### State machine I: new execution id (intent AC12, Q7)
Up to three draws:
- `id = execution_ids.new_execution_id(started_at)`;
- `validate_ingest_execution_id(id)` (`ValueError` -> `NOT_STARTED`);
- `read_run(id)` must raise `PersistenceNotFoundError`;
- `store.list_observation_sequences(id)` must be `()`.

After three taken ids -> `NOT_STARTED`. The check and `start_run` happen under the exclusion. Sequences start at 1, with no gaps (P step 3).

A check that cannot be made (Revision 7, audit finding F-15): `read_run(id)` raising a `PersistenceError` other than `PersistenceNotFoundError` (a refusal, or a `PersistenceConnectionError`), or `store.list_observation_sequences(id)` raising `OSError` or `EvidenceIntegrityError` -> `NOT_STARTED` (exit 1), no `start_run`, no new connection, nothing written, and a fixed message naming that id (suggested: `the execution id <id> could not be checked`). The database case also gets the required progress line (`read_run`, that id).

### F1 port extension: `list_observation_sequences` (intent AC22, Q14)
- Returns the sequence numbers of the files `observations/<execution_id>/<n>.json` under the root, as a sorted tuple, where `<n>` is the canonical decimal form of a non-negative integer (no sign, no leading zero except `0` itself). It does not stop at a gap.
- `ValueError` for an id that fails `validate_execution_id`, before any file system access.
- `()` when `observations/<execution_id>` does not exist; nothing is created.
- `EvidenceIntegrityError` naming the execution, and no content, for:
  - an entry of that directory that is not a regular file named `<n>.json` (`x.json`, `01.json`, a subdirectory);
  - a non-directory at that path.
- `OSError` from listing propagates unwrapped (RE-7).
- It reads no file contents, follows the existing layout only, never lists `tmp/` or `objects/`, and writes, renames or deletes nothing.
- Unchanged guarantees: RE-1 to RE-11, write-once publication, no deletion, integrity on read (RE-7, RE-8, RE-10), and `store`, `read_content` and `read_observation` byte for byte.

### F3 port extension: `list_runs` and the ingest exclusion (intent AC23, Q4)

## Proposed approach
Revisable by the executor if it records why, except where a passage cites a gate 1 decision (Qn) or a finding: only the human changes those.
- Decision: the use case opens the repository through `RepositoryOpener` — rationale: Q3 needs exactly one new connection created by the code that knows which operation is pending; `interfaces` still decides which adapter is built (intent AC18); rejected: `interfaces` passing a ready repository plus a reconnect callback (two objects for one concern).
- Decision: `IngestReporter` instead of `print` in `application` — rationale: `application` holds no I/O, and `interfaces` needs to learn the run id before the outcome so it can print `<id> running` after a second Ctrl+C; rejected: returning the id only in `IngestOutcome` (lost when the cleanup is interrupted).
- Decision: the listing returns sequence numbers, not observations — rationale: a corrupt record is reported per sequence by `read_observation` and never hides later ones (Q14, intent AC22); rejected: returning `Observation` objects (the first corrupt file would stop the listing).
- Decision (decision P-3 of the human, 2026-10-15; not revisable by the executor): `last-page-reached` is appended whenever the completed page `p` satisfies `p >= result.pages`, with no condition on `scope.last_page`, after that page's `page-completed`, and the run then ends `succeeded` — rationale: the event records that the source has no page after `p`, which is true whatever the scope says, and a resumption relies on it (intent AC3, AC24); rejected: the Revision 1 rule, which added a condition on `scope.last_page` (the no-results scope 1 to 1 would end without the event).
- Decision: the gap check runs after every listed sequence is verified — rationale: intent AC10 says a later observation is verified and not hidden by the gap.

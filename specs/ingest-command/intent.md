# Intent: Ingest command (F4)

Revision: 6
Approval: Approved revision 6 by Vladimirjon on 2026-10-15 (gate 1: design, criteria and execution order; no claim that F4 is implemented or tested)

## Outcome
The `ec-procurement-quality` CLI gains an `ingest` command that runs one
bounded ingestion of the SERCOP buyer-name search: it asks the source for a
named range of pages through the F2 adapter, keeps every response it receives
as raw evidence in the F1 local store at the fixed `data/raw/` of the
repository root (resolved once to an absolute path at start; the command is
supported only when run from the repository root), and records the
run, the hash and size of each piece of evidence, each observation and an
audit trail in PostgreSQL through the F3 adapter. Repeating the same scope
creates a new, separately audited run without duplicating evidence; a run that
fails or is interrupted leaves what it completed, and an explicit resumption
(`ingest --resume <id>`) reconciles the local store with PostgreSQL, links
itself to the earlier run and continues from the first page that is not
recorded as completed. Only one ingest is active per database at a time. The
exit code says whether the scope finished (0), a run failed, could not start
for an operational reason, or a resumption chain that exists was found cyclic,
malformed or contradictory (1), the command, its configuration or its
resumption target was invalid, including a target that does not exist or
needs no resumption (2), or the operator interrupted it with Ctrl+C (130),
and nothing printed
holds a secret or response content. This is the first code that calls the F1
store, the F2 adapter and the F3 runner and adapter together; it extends the
F1 store port with a listing of a run's observations and the F3 repository
port with a listing of runs by status and an ingest exclusion, both authorized
by the human at gate 1, and it adds to the F3 errors `MigrationLockError`, a
subclass of `MigrationError` raised only when the migration lock is busy,
authorized by the human on 2026-10-15.

### Human criteria (verbatim input)
The human wrote these criteria on 2026-10-14 (Day 18, `docs/learning/plan.md`
"Escribe tú los criterios de éxito"). They are input to this spec and are not
edited here. The acceptance criteria below are derived from them; where a
criterion left a gap or met a rule of F1 to F3, the point is listed in
§ Open questions "Findings for the human" together with the gate 1 decision
that answers it.

```text
Idempotencia: si ejecuto ingest dos veces con el mismo alcance, se crea una ejecución distinta con un execution_id nuevo, porque cada intento debe quedar auditado. Sin embargo, no se duplican los bytes de evidencia cruda ni la fila de raw_evidence cuando el contenido tiene el mismo hash. Cada ejecución sí conserva sus propias observaciones y eventos de auditoría. Cuando exista la normalización de F5, tampoco deberán duplicarse los registros normalizados. Ambas ejecuciones pueden terminar correctamente; repetir el alcance no debe producir un error por sí solo.

Reanudación: si la ejecución se interrumpe a mitad por Ctrl+C, una caída de red o una caída de PostgreSQL, las páginas que ya quedaron completamente registradas se conservan. Antes de continuar, el sistema debe reconciliar lo existente en data/raw/ y PostgreSQL, porque una caída puede ocurrir entre ambas escrituras. Después se crea una nueva ejecución, vinculada mediante auditoría con la anterior, y se continúa desde la primera página que no conste como completada, sin volver a descargar las páginas ya confirmadas. La ejecución anterior se marca como failed si todavía hay conexión; si la base estaba caída y quedó como running, debe reconciliarse y cerrarse como failed al recuperar la conexión. No debe quedar running indefinidamente ni asumirse que una operación no ocurrió solo porque se perdió la conexión durante el COMMIT.

Fallo parcial: si una página falla, cualquier respuesta recibida —por ejemplo 429, 500 o un cuerpo incompleto— se guarda primero como evidencia cruda. Después se registra el fallo y la ejecución se detiene; no se salta la página para continuar con las siguientes, porque eso dejaría un lote incompleto difícil de reproducir. La ejecución termina como failed y una reanudación empieza nuevamente desde esa página. Si el fallo ocurre antes de recibir una respuesta, no existe contenido que guardar, pero sí debe quedar un evento de auditoría. El adaptador actual no reintenta por sí mismo; si F4 incorpora reintentos, deberán ser acotados y, al agotarse, aplicarse esta misma regla

Códigos de salida: 0 significa que todo el alcance terminó correctamente y la ejecución quedó como succeeded; 1 significa que la ejecución comenzó, pero no pudo completarse por un error de la fuente, del almacenamiento, de PostgreSQL o de integridad, y quedó como failed; 2 significa que el comando, sus argumentos o su configuración eran inválidos y la ejecución no llegó a comenzar.

Evidencia: en data/raw/ deben quedar los bytes exactos de cada respuesta recibida, almacenados una sola vez según su SHA-256, y un archivo JSON de observación por cada respuesta obtenida. La observación registra la ejecución, secuencia o página, URL, estado HTTP, fecha, hash, tamaño y encabezados permitidos. También se conservan las respuestas de error o incompletas; nunca se sobrescriben  En PostgreSQL deben quedar la ejecución con su alcance y resultado, el hash y tamaño de cada evidencia, las observaciones asociadas y los eventos de auditoría. Los bytes completos no van en PostgreSQL. Al terminar correctamente, la ejecución queda succeeded; ante un fallo, queda failed, salvo que una caída de la propia base obligue a reconciliar temporalmente una ejecución running.
```

Mapping of the criteria to the ACs: Idempotencia -> AC1, AC2, AC12,

## Acceptance criteria
Conventions for every AC. All data is synthetic: the source base URL is
`https://source.invalid/PLATAFORMA`, the buyer `SYNTHETIC BUYER S.A.`, the
year `2025`. *The simulated source* is `SercopSource` with an
`httpx.MockTransport` handed in through a composition seam, under a guard that
fails the test on any socket or name-resolution attempt; *page bodies* are
synthetic bodies in the observed search shape (`total`, `page`, `pages`,
`data`), built by the test or taken from `tests/fixtures/sercop/`; unless an AC
gives another value, they report `pages` 9, above every scope's last page in
these examples, so the AC3 rule does not end a run early. *The test
store* is a `LocalDiskRawEvidenceStore` on a temporary directory, handed to the
use case or to the CLI composition by injection; the CLI itself has no option
for the store root (decision Q8), and no test touches the real `data/raw/` of
the repository (AC25 runs the CLI's own resolution from a *synthetic
repository root*: an isolated temporary directory that stands for the
repository root and holds a copy of the `migrations/` files the command needs).
Paths such as `observations/<A>/1.json` are relative to the test store's root.
*The database* is a throwaway database as in PT-13, never the one named by
`POSTGRES_DB`. `<A>`, `<B>` and `<C>` stand for generated execution ids. *Both
stores* means the local raw evidence store and PostgreSQL. *A completed page*
is defined by decision Q14. *The ingest exclusion* is the guarantee of
decision Q4 that one ingest at a time is active per database. The command is
written without the program name, so `ingest --year 2025` means
`ec-procurement-quality ingest --year 2025`, called in process through
`main([...])` (CLI-3). Each AC names the gate 1 decisions it implements.

- **AC1** (success) `ingest` requests the pages of its scope in order, stores each response in both stores, and ends `succeeded` with exit code 0.
  Example: `ingest --year 2025 --buyer "SYNTHETIC BUYER S.A." --first-page 1 --last-page 2`, the simulated source answering pages 1 and 2 with `200` page bodies whose `pages` is 3 -> exactly two requests, for page 1 then page 2; in the test store, one object per distinct body and the observation files `observations/<A>/1.json` and `observations/<A>/2.json` (execution, sequence, method, URL with the page in its query, status, capture time with its UTC offset, hash, size, headers without `Set-Cookie`; RE-3, RE-6); in PostgreSQL, run `<A>` with status `succeeded`, a `finished_at` and the AC13 scope, one `raw_evidence` row per distinct body (hash and size, no bytes), two `observation` rows equal to the local observations, and the AC13 events `run-started`, `page-completed` (page 1, sequence 1) and `page-completed` (page 2, sequence 2), in that order; exit code 0; stdout `<A> succeeded` (AC15).
- **AC2** (idempotency) Repeating a scope creates a new run with a new execution id, keeps one object and one `raw_evidence` row per content, gives each run its own observations and events, and both runs succeed.
  Example: the AC1 command run twice with the same page bodies -> runs `<A>` and `<B>`, `<A>` different from `<B>`, both `succeeded`, both exit 0; the files under `objects/` are the same before and after the second run, with the same bytes and modification times (RE-4); the `raw_evidence` row count is unchanged; four `observation` rows (two per run) and `observations/<B>/1.json`, `2.json`; `<B>` has its own `run-started` and two `page-completed` events and `<A>`'s events are unchanged. With page 2's body changed for the second run -> one new object and one new `raw_evidence` row, and both runs still succeed.
- **AC3** (end of the result set; Q10, decision P-3 of 2026-10-15) No page above the last page that the source reports is requested, and reaching it is not a failure. Whenever a completed page `p` is at or beyond the last page the source reports (`p >= pages`, which includes every beyond-the-last-page result of SA-4), the run appends `last-page-reached` (page `p`, `pages`), requests nothing more and ends `succeeded`, whatever the scope's last page is. This holds across a resumption chain: a resumption never requests a page above the `page` of the chain's one *valid* `last-page-reached` event. The validity rules are in AC24; they include that every page of the scope from its first page up to that `page` was completed earlier in the chain, so after a valid event no page of the scope is still pending; an event that fails them never makes a page be skipped, it makes the chain malformed (AC9, AC24).
  Example: scope pages 1 to 5, the source reporting `pages` 2 -> requests for pages 1 and 2 only, an event `last-page-reached` (page 2, `pages` 2), status `succeeded`, exit 0. Scope pages 1 to 2 with `pages` 2 (the reported last page equals the scope's last page) -> requests for pages 1 and 2, `last-page-reached` (page 2, `pages` 2), `succeeded`, no further request, exit 0. Scope pages 4 to 5 with `pages` 2 -> one request, for page 4, whose beyond-the-last-page result (SA-4) is stored and recorded as completed, then `last-page-reached` (page 4, `pages` 2), `succeeded`, exit 0. A search with no results (`total` 0, `pages` 0), scope pages 1 to 1 -> one request, page 1 recorded as completed, `last-page-reached` (page 1, `pages` 0), `succeeded`, exit 0. A completed page `p` with `p < pages` does not end the run; so a run that reaches the end of its scope without the event is exactly one whose every completed page had `p < pages` (AC1 uses `pages` 3 for a scope ending at page 2). In the order the run writes them, `page-completed` for page `p` comes first, then `last-page-reached` for the same page, then `finish_run`.
- **AC4** (partial failure with a response; Q2) When a page fails and a response was received, that response is stored in both stores first, then the failure is recorded, the run stops without requesting later pages, and it ends `failed` with exit code 1.
  Example: scope pages 1 to 3; page 1 answers a `200` page body; page 2 answers, in four separate cases, `429` with a synthetic HTML body, `500` with an empty body, a `200` whose body is the first half of a valid page body (SA-7), or a `200` whose transfer is cut off by a protocol error after 100 bytes (SA-6) -> page 1 has `page-completed`; page 2's response is in `observations/<A>/2.json` and in PostgreSQL with its status as received and exactly the bytes received (`size` 0 for the empty body); after it, an event `page-failed` (page 2, sequence 2, the failure kind of AC13); no request for page 3; run `failed`; exit 1; stdout `<A> failed`. A use-case test with recording doubles shows the order: local store, then PostgreSQL observation, then the page event, then `finish_run`.
- **AC5** (partial failure without a response; Q7) A failure before any response arrives records an audit event and no observation, uses no sequence number, and ends the run `failed` with exit code 1.
  Example: as AC4, but page 2 raises a connect error before the status arrives, or answers status `600` (SA-6: no response is kept) -> no file `observations/<A>/2.json` and no PostgreSQL observation for sequence 2; an event `page-failed` (page 2, sequence `None`, failure `transport`); run `failed`; exit 1.
- **AC6** (storage and integrity failures; Q2) A failure of the local store or an integrity error stops the run, ends it `failed` with exit code 1, and never treats an `OSError` from the store as proof that nothing was written (raw-evidence N2).
  Example: (a) a regular file sits at `<test store root>/observations` when page 2 is stored -> `store` raises `OSError` and no observation file exists (RE-9); an event `storage-failed` (page 2, sequence 2, store `raw-evidence`); run `failed`; exit 1. (b) A store double publishes the observation for `<A>` sequence 2 and then raises `OSError` -> the use case asks the store port for that observation (`read_observation`), finds it, and records it in PostgreSQL before the run is closed, so both stores hold it; run `failed`; exit 1. (c) With a fixed id source and an id that passed the AC12 check, a test double of the repository refuses `record_observation` of `<A>` sequence 1 with `PersistenceIntegrityError` -> an event `storage-failed` (page 1, sequence 1, store `postgresql`); run `failed`; exit 1; stderr names the operation and the identity only.
- **AC7** (interruption by Ctrl+C; Q9, Q11) An interruption keeps what was completed, makes a best-effort attempt to audit and close the run `failed`, and exits 130.
  Example: `KeyboardInterrupt` raised by the transport while page 2 is requested, with PostgreSQL reachable -> page 1 has `page-completed`; an event `run-interrupted` (page 2); run `failed`; exit code 130; stdout `<A> failed`. Raised after page 2's response was stored locally and before it was recorded in PostgreSQL -> the cleanup records that observation in PostgreSQL before it closes the run. When the cleanup cannot finish (a second `KeyboardInterrupt` during it, or the database unreachable) -> exit 130, the run may stay `running` (stdout `<A> running`), and AC10 closes it at the next `ingest`. Nothing guarantees that the cleanup completes.
- **AC8** (PostgreSQL lost during a run; Q3, decision P-2 of 2026-10-15) A lost database connection never leads the command to assume that the lost write did not happen; on exactly one new connection it takes the ingest exclusion again, repeats only idempotent operations with exactly the same values, and closes the run `failed`; when it cannot, it leaves the run `running` for reconciliation. Every connection loss exits 1, with one exception: when the operation lost is the final `finish_run(succeeded)` and its exact repeat on the new connection returns the run as `succeeded` with the same `finished_at`, the run is confirmed `succeeded` and the exit code is 0 (stdout `<A> succeeded`). "Confirmed" means only that successful repeat; F3 returns the stored run for a repeat with the same status and finish instant and refuses anything else (PS-7), so the repeat itself proves the stored state.
  Example (final `finish_run(succeeded)`, P-2): the connection is lost before that `finish_run` commits -> the repeat on the new connection finishes the run, `succeeded`, exit 0; the same, but the new connection cannot be opened or the exclusion cannot be taken again -> the run stays `running`, exit 1, stdout `<A> running`; the connection is lost after that `finish_run` committed (outcome unknown to the process) -> the idempotent repeat returns the stored `succeeded` run, exit 0.
  Example (integration): the adapter's server session is terminated (`pg_terminate_backend`) while page 2 is requested -> (a) the new connection opens and takes the exclusion: an event `storage-failed` (page 2, store `postgresql`) is appended, run `failed`, exit 1, stdout `<A> failed`; (b) new connections to that database are refused: no second attempt is made, run stays `running`, exit 1, stdout `<A> running`, and nothing in the test store is removed; (c) the new connection opens but another session holds the exclusion: the run is not touched (no event, no `finish_run`), exit 1, stdout `<A> running`. Example (unit, repository double): `record_observation` or `finish_run` commits and then raises `PersistenceConnectionError` -> on the new connection the same call is repeated with the same values (the same `finished_at` included), and the stored row is unchanged by the repeat; `append_audit_event` commits and then raises `PersistenceConnectionError` -> the run holds that event exactly once, because it is appended again only when `list_audit_events` shows no event with the same type, detail and occurrence instant; `append_audit_event` raises before committing -> the event is appended once on the new connection.
- **AC9** (resumption; Q13, Q14) `ingest --resume <id>` creates a new run with the scope of the run it resumes, links it to that run through an audit event, requests nothing that the chain of earlier runs completed, and starts at the first page not completed.
  Example: run `<A>` (pages 1 to 4) completed pages 1 and 2 and failed on page 3 -> `ingest --resume <A>` -> run `<B>` whose scope is the same JSON value as `<A>`'s (`same_json`); its `run-started` event has detail `{"resumes": "<A>", "first_page": 3}`; requests for pages 3 and 4 only; `<B>`'s sequences start at 1; `<B>` `succeeded`, exit 0. If `<B>` fails on page 4, `ingest --resume <B>` -> run `<C>` requests page 4 only. A page whose response was stored in both stores but has no `page-completed` event (process killed between the two), and a page that has only an orphan object and no observation, are requested again; identical bytes add no object and no `raw_evidence` row. Resuming a run whose every page was completed but which was left `running` -> AC10 closes it `failed`, and the resumption requests nothing and succeeds; its `run-started` has `first_page` equal to the scope's `last_page + 1` (decision P-4 of 2026-10-15), a sentinel valid only for a resumption with nothing left to request. A page above the `page` of the chain's valid `last-page-reached` event (AC24) is not left to request (AC3 holds across a chain), and a valid event also proves that every page up to its `page` was completed (AC24, coverage), so a resumption of such a run requests nothing and succeeds; an event that is not valid makes the chain malformed instead (AC24, exit 1) and never makes a page be skipped. An invalid resumption target is a usage error, exit 2, with nothing created (AC14): `--resume` together with any scope option; an id outside the F1 pattern (`Synthetic_Id`); a well-formed id that names no run (`ingest-20261014t150000z-ffffffff` on a database without it); a `succeeded` run, which needs no resumption. The target is checked right after the ingest exclusion is taken and before reconciliation, so these cases write nothing beyond the pending migrations of AC16. A chain that exists but is cyclic, malformed or contradictory is AC24 (exit 1). Resuming while another session holds the exclusion -> exit 1, nothing changed.
- **AC10** (reconciliation before continuing; Q4, Q14) Before it creates its own run, every `ingest`, holding the ingest exclusion, reconciles each run that PostgreSQL lists as `running`, using the fixed store and the F1 listing of AC22: it verifies every PostgreSQL observation against the local store, records in PostgreSQL every observation present only in the local store, and closes the run `failed`. A run whose process still holds the exclusion is never touched.
  Example (integration, crash between the two writes): run `<A>` is `running`, PostgreSQL holds its observations 1 and 2, and the test store lists observations 1, 2 and 3 for `<A>` -> the next `ingest` records observation 3 in PostgreSQL, appends `observation-reconciled` (sequence 3) and `run-closed-by-reconciliation` (`reconciled_observations` 1) to `<A>`, finishes `<A>` as `failed`, and only then starts its own run. Each of these cases -> an event `reconciliation-failed` with the sequence and one problem value of the closed list of Q6, `<A>` finished `failed`, no new run is created, exit 1:
  - PostgreSQL holds observation 2 and the store lists no observation 2 (`local-observation-missing`);
  - the stored observation 2 differs from PostgreSQL's (`local-observation-different`);
  - `observations/<A>/2.json` is not a valid record (`local-observation-unreadable`);
  - the object of observation 1 is missing (`object-missing`) or no longer matches its hash (`object-integrity`, RE-7);
  - the store lists observations 1 and 3 and no 2, with PostgreSQL holding only 1 (`sequence-gap`); observation 3 is still verified and not hidden by the gap;
  - PostgreSQL refuses a local-only observation (`postgresql-observation-conflict`);
  - the listing itself fails, for example because of an entry that is not a valid observation name (`local-listing-failed`, sequence `None`).

  While a separate session holds the exclusion, `ingest` exits 1, `<A>` stays `running`, no file is written and no run is created. After a successful reconciliation no run that PostgreSQL listed as `running` remains `running`. An orphan object (an object without an observation) is left in place and counts for nothing.
- **AC11** (finished runs are closed to additions; Q5) Once a run is `succeeded` or `failed`, no `ingest` adds an observation or an audit event to it.
  Example: after AC4 and the AC9 resumption of `<A>`, the observation and event counts of `<A>` are the same as when it was finished; the link to `<A>` lives only in `<B>`'s `run-started` event. A `--resume` whose chain fails AC24 adds nothing to any run of the chain.
- **AC12** (identities; Q7) Execution ids are new for every run, follow the F1 pattern and are never a Windows reserved device name; a new id is checked against both stores through their ports before `start_run`; sequences number the responses a run obtains, from 1, without gaps.
  Example: two invocations -> ids of the form `ingest-20261014t150000z-0a1b2c3d`, different from each other, matching `[a-z0-9][a-z0-9-]{0,63}` and none equal to `con`, `prn`, `aux`, `nul`, `com1` to `com9` or `lpt1` to `lpt9`. An id source double that first returns an id for which `read_run` finds a run, or for which the store port's listing (AC22) returns an observation -> that id is not used, a new one is drawn, and `start_run` is never called with the taken id, so a colliding id can never join an existing run (finding 18). The check and `start_run` both happen while the ingest exclusion is held. A run whose page 2 failed without a response and that obtained no other response has sequence 1 only. Every time written (`started_at`, `finished_at`, `occurred_at`, `captured_at`) carries a UTC offset and comes from the one injected clock. `application` reaches the store only through the `RawEvidenceStore` port, never through paths or directories.
- **AC13** (scope and audit catalogue; Q6) The scope is a JSON object with exactly the keys of Q6 and no float, and every audit event has a type from the closed Q6 catalogue with a detail that holds only identities, numbers and fixed words.
  Example: the AC1 run -> scope `{"scope_version": 1, "source": "sercop-search-ocds", "base_url": "https://source.invalid/PLATAFORMA", "buyer": "SYNTHETIC BUYER S.A.", "year": 2025, "first_page": 1, "last_page": 2}`, compared with `same_json`. Across every AC, each event type is one of the Q6 catalogue, each `failure`, `store` and `problem` value is one of its closed lists, and no detail holds a URL, a header value, body bytes, a setting or the text of an exception message.
- **AC14** (usage, configuration and resumption-target errors; Q8, Q9, Q13) An invalid command, argument, configuration or resumption target exits 2 before anything is requested or started.
  Example: no `--last-page`; `--first-page 0`; `--last-page 1 --first-page 2`; `--year 0` or `--year abc`; an empty `--buyer`; `--raw-root <path>` (the option does not exist: `unrecognized arguments`); `--resume Synthetic_Id`; `--resume <id>` with `--year`; `POSTGRES_DB`, `POSTGRES_USER` or `POSTGRES_PASSWORD` unset; `POSTGRES_PORT` set to `abc` or `70000`; a migrations directory that does not exist or holds an invalid file (PS-3) -> exit 2, stdout empty, stderr a message naming the argument or variable and never its value, no request to the simulated source, no file in the test store, no connection to the database, and no run in it. `--resume` with a well-formed id that names no run, or with a `succeeded` run -> exit 2, stdout empty, stderr a fixed message naming the execution id, no request, no file written, no event appended and no run created or finished. The pending migrations of AC16 may already have been applied in these cases; nothing else is written. A bare `ec-procurement-quality` -> usage on stderr, exit 2. A `.env` file in the current directory is never read: with the variables unset and a `.env` present, the result is the same exit 2. `POSTGRES_HOST` and `POSTGRES_PORT` are optional (AC25).
- **AC15** (output and secrets; Q9, Q11) stdout carries only the result line of a run, stderr carries progress and errors without secrets or response content, and nothing prints a traceback or an exception chain.
  Example: stdout is exactly one line `<id> <status>` (status `succeeded`, `failed` or `running`) whenever this invocation created a run, whatever the exit code (0, 1 or 130), and is empty otherwise. `<status>` is the last status this process confirmed for its run; `running` means that closing the run was not confirmed (decision P-5 of 2026-10-15), not a claim that PostgreSQL still holds `running`: after a second Ctrl+C during the cleanup (AC7), the line is `<id> running` even if a `finish_run` may have committed unseen. After the P-2 case of AC8 the line is `<id> succeeded` with exit 0. With the password `synthetic-password-marker`, a page body holding `synthetic-body-marker`, a header value `synthetic-header-marker` and a `Set-Cookie: synthetic-session=s1` -> none of the markers or the cookie value appears in stdout, stderr or any stored audit detail, and stderr holds no URL. A transport double raising a synthetic exception that is not a project error, whose message holds `synthetic-body-marker` -> stderr names only the exception's class, an event `unexpected-error` (page, class name) is appended, run `failed`, exit 1. A `MemoryError` from the transport -> the same, best effort (Q11): if the cleanup cannot audit or close, the run may stay `running`, exit 1. During every run the effective level of the `httpcore` logger is above `DEBUG` (R-7), and `ingest` adds no logging handler.
- **AC16** (migrations; Q1, decision P-1 of 2026-10-15) `ingest` applies the pending migrations of its migrations directory before it creates the repository. The runner raises `MigrationLockError`, a new subclass of `MigrationError`, exclusively when the migration lock is busy (PS-4); every other runner refusal stays a plain `MigrationError`. `ingest` exits 1 for `MigrationLockError` and 2 for any other `MigrationError`. The error's message keeps its fixed, secret-free text (`another migration run holds the lock`; PS-12 holds).
  Example: an empty throwaway database -> `ingest` applies `0001_initial_schema.sql` (named on stderr) and then runs as AC1; a migrated database -> nothing is applied; an incompatible directory or history (a changed, missing or renamed applied file, a gap, a bad name or content; PS-3) -> a `MigrationError` that is not a `MigrationLockError`, exit 2, no run created; another session holding the migration lock (PS-4) -> `MigrationLockError`, exit 1, stdout empty, no run created; a consumer that catches `MigrationError` still catches it. A new unit test, `tests/unit/test_persistence_error_hierarchy.py`, pins three things: `MigrationLockError.__bases__ == (MigrationError,)`; six errors in total; and the four direct descendants of `PersistenceError` unchanged (decision of the human of 2026-10-15). A separate new integration test, `tests/integration/test_postgres_migration_lock_error.py`, pins that only a busy lock produces `MigrationLockError`: every non-lock `MigrationError` case there must not be a `MigrationLockError`. A use-case or composition test shows `apply_migrations` returning before the repository is built.

- **AC24** (resumption chain integrity; Q13) When the run named by `--resume` exists and is resumable, but the chain followed from it is cyclic, malformed or contradictory, the resumption is an integrity failure: exit 1, nothing is added to any run, and no new run is created. (A target that does not exist or is `succeeded` is AC14, exit 2.)
  Example: the named run exists and is `failed` (or `running`, and is then closed by AC10), and its chain has one of these -> exit 1, stdout empty, stderr a fixed message naming the execution id, no new run, and no event added to any run beyond those of an AC10 reconciliation that ran first:
  - a `run-started.resumes` link inside the chain that names no run (malformed);
  - `<A>` resumes `<B>` and `<B>` resumes `<A>` (a cycle);
  - a run in the chain with no `run-started` event, with two, or whose detail lacks `resumes` or `first_page` or gives them the wrong type;
  - a `first_page` that the chain does not justify (decision P-4): a fresh run's (`resumes` `None`) must equal its scope's `first_page`; a resumption's must equal the first page left to request, or exactly `last_page + 1` when no page is left to request; a page is left to request when no earlier run of the chain completed it and it is not above the `page` of the chain's valid `last-page-reached` event (AC3; validity below); any other value, inside or outside the scope (for example a hand-made `last_page + 2`, `0`, or `last_page + 1` while a page is still left to request), is malformed;
  - a resumption whose `first_page` is `last_page + 1` but that holds a `page-completed` or `page-failed` event (it requested nothing, so it cannot have one);
  - a run in the chain whose scope is not `same_json` to the resumed run's scope;
  - a `page-completed` event that names a sequence with no `200` observation in both stores;
  - a `last-page-reached` event that is not valid. It is valid only when all of these hold (decisions of the human of 2026-10-15), and only a valid one may limit the pages of a resumption:
    - its detail is exactly `{"page": int, "pages": int}`: these two keys, no other, neither missing, and neither a `bool`;
    - `first_page <= page <= last_page` of the run's scope, `pages >= 0`, and `page >= pages`;
    - it is the only `last-page-reached` event of its run, and the only one in the whole chain; two anywhere in the chain are malformed, with no precedence rule (decision of the human of 2026-10-15);
    - the same run holds, earlier in its event order, a valid `page-completed` for the same page (one that passes the bullet above). The run writes `page-completed`, then `last-page-reached`, then closes (AC3);
    - no `page-completed` or `page-failed` event of that run comes after it;
    - **coverage** (required by the human on 2026-10-15): when the event for page `p` is reached, the valid `page-completed` events seen so far in the chain cover every page from the scope's `first_page` up to `p`.
      - The scope is the one the whole chain shares (`same_json`, checked above), so `first_page` is the scope's first page, not a run's `run-started.first_page`.
      - A valid `page-completed` is one that passes the bullet above: it names a page inside the scope and the sequence of a `200` observation present in both stores with the same content hash (AC1, AC5, Q14). A `page-completed` for a page below the scope's `first_page` (or above its `last_page`) is never valid, so it can neither cover nor be skipped silently: it already makes the chain malformed.
      - "Seen so far" is deterministic. The chain is walked from its oldest run (`resumes` `None`) to the resumed run, and each run's events in the order `list_audit_events` returns them.
      - If any page from `first_page` to `p` is missing, the chain is malformed.

    Consequence: after a valid event for page `p`, every page from `first_page` to `p` is completed and no page above `p` is left to request, so nothing is pending. Every later run of the chain must then be a sentinel run (`first_page` `last_page + 1`, no page events, decision P-4), which cannot hold the `page-completed` a second valid event needs. So two events can never both be valid, which is why a second one is always malformed.

    Example: each of these -> exit 1, no request to the source, no run created, nothing added to any existing run, and no page skipped: a detail with an extra or a missing key (`{"page": 2}`), a `bool` page (`{"page": True, "pages": 1}`), `page` above the scope's `last_page`, `page < pages` (`{"page": 2, "pages": 3}`), two `last-page-reached` events in one run or one in each of two runs of the chain, an event with no `page-completed` for its page in its run (or with that `page-completed` only after it), an event followed in its run by a `page-completed` or a `page-failed`, and (coverage) scope 1 to 4 with pages 1 and 4 completed, then `last-page-reached` for page 4, but no `page-completed` for page 2 or 3 anywhere in the chain. Positive controls, which are not rejected: pages 1 and 2 completed by run `<A>`, pages 3 and 4 by run `<B>`, then the event for page 4 (`pages` 4) in `<B>`; or pages 1, 2 and 3 completed across `<A>` and `<B>`, then the event for page 3 (`pages` 3) -> the chain is valid, and `ingest --resume <B>` requests nothing and succeeds with `first_page` 5.

  Reconciliation (AC10) neither reads nor validates audit events. It always runs first, so the order is deterministic: reconciliation of every `running` run, then this chain check. It only appends `observation-reconciled`, `run-closed-by-reconciliation` or `reconciliation-failed`, which are not page events. It never appends a `page-completed` (Q14: completeness is never decided from stored bytes), so the coverage check counts only the `page-completed` events that the runs themselves wrote. A run closed by reconciliation is checked here like any other, and an invalid `last-page-reached` it holds makes the chain malformed.
- **AC25** (store root and defaults; Q8, findings 19 and 21) `interfaces` resolves `data/raw/` against the current directory once, at start, to an absolute path, and uses that path for the whole invocation; `POSTGRES_HOST` and `POSTGRES_PORT` are optional, with the defaults `127.0.0.1` and `5432`.
  Example (CLI tier, no network, throwaway database): the current directory is `<T>`, a synthetic repository root: an isolated temporary directory that stands for the repository root and contains a `migrations/` directory with a copy of the repository's migration files, and the command uses the default relative `--migrations-dir` (no absolute `--migrations-dir` is given, so the test does not bypass the run-from-the-root rule); the transport double changes the current directory to another temporary directory `<U>`, which is not a repository root, while page 1 is requested -> every object and observation of the run is under `<T>/data/raw/`, nothing is created under `<U>`, and when page 2 fails, a later `ingest --resume` of that run started from `<T>` finds page 1's observation through the AC22 listing and does not request page 1 again. A composition test reads the store root that `interfaces` built and finds it absolute and equal to `<T>/data/raw`. With `POSTGRES_HOST` and `POSTGRES_PORT` unset and the other three variables set, the `PostgresSettings` that `interfaces` builds has host `127.0.0.1` and port `5432`, and no error is reported for the two absent variables. `interfaces` neither searches for a repository root nor offers an option for the store root: being at the real repository root remains the operator's responsibility, and running outside it is not supported (`<T>` is a synthetic repository root, not a supported second location).

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|

### Decisions for the human at gate 1
All fifteen were decided by the human on 2026-10-14 (gate 1 revision). The text below records what was chosen; the alternatives that were not chosen are in Revision 1.

1. **Migrations before the repository.** Decided by the human on 2026-10-14 (gate 1 revision): **option A**. `ingest` calls `apply_migrations` with its migrations directory before it creates the repository, and names the applied files on stderr. An incompatible directory or history is exit 2; a busy migration lock is exit 1, told apart by `MigrationLockError` (decision P-1 of 2026-10-15). There is no `migrate` command in this version (AC16).
2. **Write order.** Decided by the human on 2026-10-14 (gate 1 revision): **accepted as derived** from F1 to F3. The order is the local store, then `record_observation`, then the page event, then closing the run. After an `OSError` from `store`, the use case asks the store port for that observation and records a published one in PostgreSQL before closing (AC4, AC6).
3. **After `PersistenceConnectionError`.** Decided by the human on 2026-10-14 (gate 1 revision): **option A**.
   - Open exactly one new connection and take the ingest exclusion again. If either fails, the run is not touched and stays `running` for AC10.
   - Repeat only `start_run`, `finish_run` and `record_observation`, with exactly the same values.
   - Append an event again only if `list_audit_events` confirms that no event with the same type, detail and instant exists.
   - Then record the failure and close the run `failed` (AC8).
4. **One active ingest per database.** Decided by the human on 2026-10-14 (gate 1 revision): **option A**. The human authorizes the persistence extension of AC23: (a) list runs by status; (b) an ingest exclusion that one repository holds for the whole invocation. The `application` port expresses only the exclusion; the PostgreSQL advisory lock that implements it, its key (distinct from `MIGRATION_LOCK_KEY`) and its try-only, never-waiting behavior are `infrastructure` details. Under the exclusion, every `running` run belongs to a process whose session is gone, so it is reconciled and closed `failed` (AC10), even if every page was completed.
5. **Additions after a run finished.** Decided by the human on 2026-10-14 (gate 1 revision): **option A**. After `finish_run`, no observation or event is added to that run; reconciliation finishes its work before `finish_run`, and the resumption link lives on the new run (AC11).
6. **Event catalogue and scope.** Decided by the human on 2026-10-14 (gate 1 revision): **the proposed catalogue and scope, accepted**. The catalogue is closed; types are kebab-case. Details hold `int`, `str` and `None` only, with no URL, header value, body, setting or exception message text.
   - `run-started` `{"resumes": <execution id> or None, "first_page": <int>}`;
   - `page-completed` `{"page", "sequence", "content_hash"}`;
   - `page-failed` `{"page", "sequence" (int or None), "failure", "status" (int or None)}`, where `failure` is one of `status`, `incomplete`, `transport`;
   - `storage-failed` `{"page", "sequence" (int or None), "store"}`, where `store` is one of `raw-evidence`, `postgresql`;
   - `last-page-reached` `{"page", "pages"}`;
   - `run-interrupted` `{"page"}`;
   - `unexpected-error` `{"page", "error_type"}`, where `error_type` is the exception's class name only;
   - on a run being reconciled: `observation-reconciled` `{"sequence"}`, `run-closed-by-reconciliation` `{"reconciled_observations"}`, and `reconciliation-failed` `{"sequence" (int or None), "problem"}`;
   - `problem` is one of the closed list `local-observation-missing`, `local-observation-different`, `local-observation-unreadable`, `object-missing`, `object-integrity`, `sequence-gap`, `postgresql-observation-conflict`, `local-listing-failed`.

   Scope: `{"scope_version": 1, "source": "sercop-search-ocds", "base_url", "buyer", "year", "first_page", "last_page"}`, integers and text only, compared with `same_json`; a resumption copies its original's scope (AC13).
7. **Execution ids, sequences and the clock.** Decided by the human on 2026-10-14 (gate 1 revision): **accepted**.
   - Ids have the form `ingest-<UTC start, yyyymmddThhmmssZ in lowercase>-<8 lowercase hex characters from a random source>`, 33 characters, off every Windows reserved name.
   - Before use, `read_run` must report the id unknown and the store port's listing (AC22) must return nothing for it, both under the exclusion; otherwise another id is drawn. The check goes through the `RawEvidenceStore` port, never through paths or directories in `application`.
   - Sequences start at 1 and grow by one per response obtained, with no gaps; an attempt that obtains no response uses no number.
   - `application` declares a clock port and an id-source port; `interfaces` gives the real ones (the same clock also goes to `SercopSource(now=...)`), and tests give fixed ones (AC12).
8. **Configuration.** Decided by the human on 2026-10-14 (gate 1 revision).
   - `interfaces` reads only the process environment: `POSTGRES_HOST` (optional, default `127.0.0.1`; `.env.example` stays without it), `POSTGRES_PORT` (optional, default `5432`), `POSTGRES_DB`, `POSTGRES_USER` and `POSTGRES_PASSWORD` (the last three required). It reads no `.env` and adds no dependency; the human runs `uv run --env-file .env ec-procurement-quality ingest ...`.
   - A missing or malformed variable is exit 2, naming the variable and never its value.
   - `--migrations-dir` stays, default `migrations`.
   - There is no option for the store root: the store of this version is the fixed `data/raw/`, because the root is not recorded in a run's scope and a variable root would prevent reconciling earlier runs. Tests receive a temporary store by injection.
   - `ingest` is supported only when run from the repository root (finding 21, decided by the human on 2026-10-14); `interfaces` resolves `data/raw/` once, at start, to an absolute path, with no root detection (AC25).
   - There is no option for the base URL; tests substitute the source in process.
9. **CLI contract and exit codes.** Decided by the human on 2026-10-14 (gate 1 revision): **option A**.
   - Command: `ingest --year <int> --buyer <text> --last-page <int> [--first-page <int>, default 1] [--migrations-dir <path>]`, or `ingest --resume <execution id> [--migrations-dir <path>]`. The subcommand is not a required `argparse` argument, so CLI-2 keeps its message; a bare command is a usage error.
   - Order of an invocation: arguments, environment and the absolute store path (2) -> migrations (2 or 1) -> repository (1) -> ingest exclusion (1) -> for `--resume`, the target check (2) -> reconciliation of `running` runs (1) -> for `--resume`, the chain checks (AC24, 1) -> new id and its check -> `start_run` and `run-started` -> pages -> `finish_run`.
   - 0: the run is `succeeded`, including a run confirmed `succeeded` by the exact repeat of its final `finish_run` after a lost connection (decision P-2 of 2026-10-15).
   - 1: a run was created and ended `failed`, or was left `running` when PostgreSQL could not be reached or the exclusion could not be taken again; also an operational failure before any run was created, or a resumption chain that exists but is cyclic, malformed or contradictory, with stdout empty.
   - 2: an invalid command, argument or configuration, including migration files or recorded migrations that do not match (PS-3), or an invalid resumption target (a malformed id, a well-formed id that names no run, a `succeeded` run), found before any run was created.
   - 130: interrupted by Ctrl+C.
   - stdout: exactly `<id> <status>` when a run was created, nothing otherwise.
   - stderr: usage errors, progress lines naming page, sequence, status and content hash, and error lines with the fixed message of a project error or only the class name of any other exception; never a traceback, chain, URL, header value, body, setting or password.
10. **Bounded scope.** Decided by the human on 2026-10-14 (gate 1 revision): **accepted**. The scope is always an explicit page range; `--last-page` has no default; there is no extra limit on the range's length; no request goes above the `pages` the source reports (AC3). The Day 20 live run is the human's manual step: `--year 2025 --buyer "EMPRESA ELÉCTRICA QUITO S.A. E.E.Q." --first-page 1 --last-page 3`. No test touches the real network, the real `data/raw/` or the configured database (AC19).
11. **One adapter instance; Ctrl+C and `MemoryError`.** Decided by the human on 2026-10-14 (gate 1 revision): **accepted**. One `SercopSource` and one repository per invocation, used from one thread, never called from the transport or injected callables (SA-13, PS-13), and both closed at the end. The cleanup after `KeyboardInterrupt` or `MemoryError` is best effort: it tries to record a published observation, append `run-interrupted` or `unexpected-error`, and close the run. If it cannot, the run may stay `running` for later reconciliation; nothing guarantees otherwise (AC7, AC15).
12. **Retries.** Decided by the human on 2026-10-14 (gate 1 revision): **option A**. F4 does not retry inside a run; `ingest --resume` is the audited new attempt (AC17).
13. **How a resumption is started.** Decided by the human on 2026-10-14 (gate 1 revision): **option A**. Resumption is explicit with `ingest --resume <id>`, which copies the original scope; any scope option with it is a usage error, and a plain `ingest` always fetches its whole scope. A target that is malformed, names no run or is `succeeded` is invalid input: exit 2, nothing created (AC14; finding 22, decided by the human on 2026-10-14). A chain that exists but is cyclic, malformed or contradictory is an integrity failure: exit 1, no new run (AC24).
14. **Completed pages and how reconciliation finds observations.** Decided by the human on 2026-10-14 (gate 1 revision).
   - The completed-page definition of option A is kept: a page is completed for a run when that run holds a `page-completed` event naming the page and the sequence of a `200` observation present in both stores. The completed pages of a resumption are those of every run in its chain, followed through `run-started.resumes`. Reconciliation never decides completeness from bytes.
   - To find observations, **option C**: the `RawEvidenceStore` port gains a listing of one execution's observations (AC22). Probing until the first `EvidenceNotFoundError` is rejected, because a gap caused by corruption could hide later observations.
   - Orphan objects are kept and never count as a completed page.
   - The same valid `page-completed` events are what the AC24 coverage check of `last-page-reached` counts (decision of the human of 2026-10-15); reconciliation never adds one.
   - Reconciliation uses the fixed store and that listing (AC10).
15. **Records by `ocid`.** Decided by the human on 2026-10-14 (gate 1 revision): **option A**. F4 handles search pages only; `api/record` is left to a later feature, possibly needed by F5.

### Decisions on the execution-plan findings (2026-10-15)
The execution plan's Revision 1 raised five points; the human decided them on 2026-10-15.

- **P-1, a busy migration lock.** Decided by the human on 2026-10-15: **accepted**. `MigrationLockError(MigrationError)` in `domain`, raised exclusively when the migration lock is busy (PS-4), with the same fixed, secret-free message. `ingest` exits 1 for it and 2 for any other `MigrationError` (AC16, AC20, Scope In).
- **P-2, a lost connection during the final `finish_run(succeeded)`.** Decided by the human on 2026-10-15: **accepted, with a contract change to AC8**. When the exact repeat of that `finish_run` on the new connection returns the run `succeeded` with the same `finished_at`, the run is confirmed `succeeded` and the exit code is 0. Every other connection loss exits 1. Confirmation is the successful repeat itself, not a separate `read_run` (AC8, Q9).
- **P-3, the no-results example of AC3.** Decided by the human on 2026-10-15: **the plan's reading was not accepted**. `last-page-reached` is appended whenever the completed page `p` satisfies `p >= pages`, whatever the scope's last page, and the run then ends `succeeded`; this covers `pages` 0 with scope 1 to 1 and a reported last page equal to the scope's last page (AC3).
- **P-4, `first_page` when nothing remains.** Decided by the human on 2026-10-15: **accepted**. `run-started.first_page` is `last_page + 1` only for a resumption with nothing left to request; the chain check accepts that value only in that case, and any other out-of-scope or unjustified value is a malformed chain (AC9, AC24).
- **P-5, stdout after an interrupted cleanup.** Decided by the human on 2026-10-15: **accepted**. stdout prints `<id> running`, where `running` is the last status the process confirmed and means that closing was not confirmed, not that PostgreSQL necessarily still holds it (AC15).

### Decisions on the hierarchy test and the P-3 consequences (2026-10-15)
- **Hierarchy test.** Confirmed by the human on 2026-10-15. The existing direct-subclass test is not edited. The new `tests/unit/test_persistence_error_hierarchy.py` pins `MigrationLockError.__bases__ == (MigrationError,)`, six errors in total, and the four direct descendants of `PersistenceError` unchanged. The separate `tests/integration/test_postgres_migration_lock_error.py` pins that only a busy lock produces `MigrationLockError` (AC16, AC20).
- **P-3 consequences.** Accepted by the human on 2026-10-15:
  - no page above a valid `last-page-reached` of the chain is requested;
  - page bodies report `pages` 9 in the other scenarios (AC conventions);
  - a `first_page` that the chain does not justify, and a sentinel run (`last_page + 1`) that holds page events, are malformed (AC24).
- **Confirmed definitively by the human on 2026-10-15:**
  - the new hierarchy test `tests/unit/test_persistence_error_hierarchy.py`;
  - `storage-failed` may follow a valid `last-page-reached`;
  - two `last-page-reached` events anywhere in the chain are rejected, with no precedence rule.
- **Coverage of `last-page-reached`.** Required by the human on 2026-10-15: a `last-page-reached` for page `p` is valid only if the valid `page-completed` events seen so far in the chain (oldest run first, events in `list_audit_events` order) cover every page from the shared scope's `first_page` up to `p`; otherwise the chain is malformed (AC24). This turns "after this event no page is left to request" into a checked fact, and it is what makes the one-event rule correct.
- **Validation of `last-page-reached` before it limits a resumption.** Required by the human on 2026-10-15. The validity rules and their examples are in AC24 (exact detail, range, one per run and per chain, a preceding valid `page-completed` of the same page, no page event after it). An event that fails them makes the chain malformed (exit 1) and never makes a page be skipped.

# Intent: SERCOP source adapter (F2)

Revision: 3
Approval: Approved revision 3 by Vladimirjon on 2026-10-10, accepting the architect's recommendation on every Revision 3 open question and on the audit's findings F-1 and F-2. Revision 2 was approved by Vladimirjon on 2026-10-10, including the decision that a status outside 100 to 599 raises a transport error without its bytes and F1's range is not widened; Revision 1 was approved by Vladimirjon on 2026-10-10

## Outcome
The system can ask the SERCOP open-contracting portal for one page of the
confirmed buyer-name search (`search_ocds`) or for one record by `ocid`
(`api/record`) and get back the response exactly as received: method, URL as
sent, status, headers and body bytes, plus the capture time. Each call sends
exactly one HTTP request and ends in one of two ways. It returns a checked
result, or it raises a typed error that still carries whatever valid response
was received (a status outside 100 to 599 is reported without one, AC6), so F4
can store every response, the failed ones included, through
the existing `RawEvidenceStore.store` (F1, ADR 0005) without changes. Nothing
else leaves a call except invalid-input and usage errors and exceptions that
are not source outcomes (AC15). F2 delivers
the port, the result and error types and the `httpx` adapter, with pacing
driven by the observed rate-limit header. It is tested only with the fixtures
and a simulated transport, never the network, and nothing calls it yet (no CLI
command, no ingestion, no storage, no normalization).

## Acceptance criteria
Sources. Every statement about SERCOP below cites a section of
[`docs/sources/sercop-observations.md`](../../docs/sources/sercop-observations.md)
("Obs. §") or is marked **project decision**. "Series" is its section
"Observation series of 2026-10-10". Fixtures are the files in
`tests/fixtures/sercop/` (README there), approved at gate 1 on 2026-10-10. Bodies for
other statuses and for truncation are **synthetic**: the test builds them, and
they say nothing about the source's own format.

Notation. `<base>` is the base URL the adapter is given. In tests it is
`https://source.invalid/PLATAFORMA`. The default is the observed
`https://datosabiertos.compraspublicas.gob.ec/PLATAFORMA` (Obs. § Confirmed
search endpoint). `<EEQ>` is the complete buyer name
`EMPRESA ELÉCTRICA QUITO S.A. E.E.Q.`, and `<EEQ%>` is its observed encoding
`EMPRESA%20EL%C3%89CTRICA%20QUITO%20S.A.%20E.E.Q.` (same section). The exact
names of types, errors and attributes are pinned in `execution-plan.md`
§ Binding constraints.

- **AC1** A search call sends exactly one `GET` with the confirmed buyer-name query, reproduced as observed: parameters `local=1` (an opaque constant with no assigned meaning), `year`, `page` and `buyer` in that order, the buyer name percent-encoded in UTF-8 with spaces as `%20`, and no keyword parameter (Obs. § Confirmed search endpoint, § Minimum pending checks). A `200` whose body passes the AC7 checks returns a search result with `total`, `page`, `pages`, the number of entries in `data`, and the raw response.
  Example: year `2025`, page `1`, buyer `<EEQ>`, transport answering `200` with the bytes of `search_single_page.json` -> exactly one request, to `<base>/api/search_ocds?local=1&year=2025&page=1&buyer=<EEQ%>`; result `total` 3, `page` 1, `pages` 1, record count 3, not beyond the last page; its raw response has method `GET`, that URL exactly, status `200`, and content equal to the fixture bytes.
- **AC2** A record call sends exactly one `GET` to `<base>/api/record?ocid=<ocid>` (Obs. § Record endpoint and rate limiting). A `200` whose body passes the AC7 checks returns a record result with the `ocid` and the number of releases, and the raw response.
  Example: `ocid` `ocds-5wno2w-SYNTHETIC-A`, transport answering `200` with the bytes of `record_single_release.json` -> request URL `<base>/api/record?ocid=ocds-5wno2w-SYNTHETIC-A`; result `ocid` `ocds-5wno2w-SYNTHETIC-A`, release count 1; content equal to the fixture bytes, with every `\/` unchanged (Series § `api/record`).
- **AC3** The raw response is the response as received. Headers are ordered `(name, value)` pairs, with names in the case received and repeated names kept in order (Series § Other response behavior). `Set-Cookie` is passed on unchanged, and the store drops it (RE-6). The content is the exact message-body bytes after chunked transfer decoding and before any content decoding (Series § Response body: chunked, no `Content-Length`). The capture time comes from an injected clock and keeps its UTC offset. The raw response's fields map one to one onto the keyword arguments of `RawEvidenceStore.store` (RE-12) apart from `execution_id` and `sequence`, so storing it needs no change to F1. No request carries a `Cookie` header, even after a response that set one (**project decision**: the observation requests carried none).
  Example: a `200` delivered in three chunks with headers `Content-Type: application/json`, `Docker-Distribution-Api-Version: registry/2.0` (twice), `X-RateLimit-Limit: 60`, `X-RateLimit-Remaining: 47` and a synthetic `Set-Cookie: synthetic-session=s1`, at injected time `2026-10-10T06:58:00-05:00` -> the headers are exactly those six pairs in that order, the content is the concatenated chunks, and `captured_at` is that time. Passing the raw response to `LocalDiskRawEvidenceStore(tmp_path).store` with an execution id and sequence succeeds, `read_content` returns the same bytes, the observation keeps the other five pairs, and the next request sent carries no `Cookie` header.
  Revision 3 (**project decision**). The adapter keeps no cookies at all: a `Set-Cookie` header stays in the raw response as received, but nothing parses it during a call, so no value in it can produce an error, a log record or a Python warning (the client's cookie jar parsed every `Set-Cookie` and, for some values, issued a warning with a traceback, which goes to stderr outside tests).
  Example (synthetic): a valid `200` whose headers add `Set-Cookie: synthetic=1; expires=01-Jan-` followed by 5,000 `9` and ` 00:00:00 GMT` -> the same result as without that header, no warning is issued during the call, and the next request carries no `Cookie` header.
- **AC4** A page beyond the last page, and a search with no results, are valid results, not errors. The result says whether the page is beyond the last page, so an empty `data` is never read as "no results" on its own (Series § Pagination).
  Example (observed): `search_page_out_of_range.json` for page 30 -> result `total` 284, `page` 30, `pages` 29, record count 0, beyond the last page, no error. Example (**inferred, not observed**): `search_no_results.json` for page 1 -> `total` 0, `pages` 0, record count 0, beyond the last page, no error.
- **AC5** (failure) Any status other than `200` (within 100 to 599, see AC6 for the rest) raises a status error that carries the complete raw response (status, headers, exact body). The adapter does not read `Retry-After`, does not parse non-`200` bodies, and does not follow redirects. The `Location` header is kept as received and never interpreted: whatever it holds (absent, relative, absolute, malformed, or longer than the HTTP library accepts as a URL), it never changes the outcome (**project decision**, Revision 2: the HTTP library parses `Location` on every redirect status even when redirects are off, and a value it cannot parse made it raise and drop the response). The requirement holds whatever a `429`, `5xx` or `3xx` contains, because none was preserved and no `3xx` was ever observed (Obs. § Record endpoint and rate limiting; Series § Still unverified after this series).
  Example (all synthetic): `429` with body `b"<html>synthetic rate limit</html>"` and `Retry-After: 1`, `500` with an empty body, `503` with `b"synthetic unavailable"`, `404` for an `ocid` (the real answer for an unknown `ocid` is unobserved), `204`, and `302` with a `Location` header -> each raises the status error, whose response has that status and exactly that body. The `302` produces exactly one request. Revision 2: body `b"synthetic redirect body"` with `302` and `Location: https:abc`, `302` and `Location: /synthetic<TAB>path` (a tab inside), `307` and `Location: http://999.1.1.1/`, and `301` with a `Location` of `/` followed by 65,530 `a` -> each raises the status error whose response has that status, that body and that `Location` header unchanged, after exactly one request. Revision 3: this holds for every value and every exception type, including a host the HTTP library cannot decode as IDNA, for which it raised an `idna.IDNAError` that escaped the call: `302` with `Location: http://xn--/` and `308` with `Location: //xn--/` -> the same status error, after exactly one request.
- **AC6** (failure) A transport failure raises a transport error and never a result. If it happens before the status and headers arrive (connection failure, timeout), the error carries no response. If it happens after them (the body is cut off, or a read times out partway), the error carries a partial raw response with the status, the headers and the bytes received so far, because a truncated body is evidence (ADR 0005).
  A message whose status is outside 100 to 599 is not a valid HTTP response (RFC 9110 § 15 calls such codes invalid) and cannot be stored by F1, which accepts only 100 to 599 (RE-11). It raises a transport error with no response, whose message names the operation and the status number (**project decision**, Revision 2; see Open questions). The raw response keeps its 100 to 599 range and F1 does not change.
  Example: the transport raises a synthetic connect error or read timeout before answering -> transport error with no response. The transport sends status `200` and then the first 100 bytes of `search_single_page.json` before raising a synthetic protocol error -> transport error whose response has status `200` and content equal to those 100 bytes. Revision 2 (synthetic): status `600`, `999` or `99` with body `b"synthetic-body-marker"` -> transport error with no response, for a search and for a record call, after exactly one request; its message contains the operation and the status number and not the body marker. No untyped `ValueError` escapes.
- **AC7** (failure) A complete `200` whose body is unusable raises an incomplete-response error that carries the complete raw response, never a partial result (ADR 0005 leaves this judgement to the adapter). Search body: it must be strict UTF-8 JSON whose top level is an object with `total`, `page` and `pages` as non-negative integers (`true` and `false` are rejected) and `data` as a list, and its `page` must equal the requested page (Series § Response body, § Pagination: "`page` echoed the requested number"). Record body: it must be strict UTF-8 JSON whose top level is an object with a non-empty `releases` list in which every release is an object whose `ocid` equals the requested one (Series § `api/record`). Nothing else is checked: not the 15 record keys, not page sizes, not other OCDS sections (F5).
  Example: the first half of `search_single_page.json` delivered as a complete body; bytes that are not UTF-8; a top-level list; `total` missing, `"3"` or `true`; `data` set to `null`; `page` 2 in answer to page 1; a gzip-compressed body with `Content-Encoding: gzip` (kept raw, so it is not JSON); and, for a record, `releases` missing, empty or not a list, a release without `ocid`, or a release whose `ocid` differs from the requested one -> each raises the incomplete-response error, and its response holds exactly the bytes sent.
  Revision 3 (**project decisions**; never observed, and the response is kept whole either way). "JSON" means JSON as RFC 8259 defines it: the constants `NaN`, `Infinity` and `-Infinity`, which RFC 8259 § 6 does not permit and Python's parser accepts by default, make a body unusable wherever they appear. A body that the standard library parser cannot read within the interpreter's default limits is unusable too, not an error of another kind: an integer of more than 4,300 digits anywhere in it (CPython's default limit for converting text to an integer), or nesting deeper than the recursion limit. When a name repeats in an object, the last value counts (RFC 8259 § 4 leaves it open; it is the value the parser keeps).
  Example (synthetic): a search body that is valid except that `data` is `[NaN]`, `[Infinity]` or `[-Infinity]`; a record body whose only release also holds `"amount": Infinity` or `"amount": NaN`; a valid search or record body that also holds an integer of 5,001 digits; a search body whose `total` has 4,301 digits; 100,000 nested `[` -> each raises the incomplete-response error with exactly the bytes sent. `{"total": 3, "page": 2, "page": 1, "pages": 1, "data": []}` for page 1 -> a valid result for page 1.
- **AC8** (failure) Nothing leaks response content. Error messages, and `str()` and `repr()` of errors and of raw responses, contain no body bytes and no header values. No error's `__cause__` or `__context__` chain holds a `JSONDecodeError` or `UnicodeDecodeError` (they keep the body text, F1 reservation N3). The adapter writes no log records of its own, and no log record emitted during a call contains body or header values.
  Example: synthetic body marker `synthetic-body-marker` and header value `synthetic-header-marker`, in a success, a `429`, an invalid-JSON `200` and a cut-off body -> neither marker appears in any message, `str()`, `repr()` or captured log record, and no record comes from an `ec_procurement_quality` logger.
  Revision 3 (the audit's reservation R-1, now a requirement). The HTTP library's own exceptions repeat parts of the URL they rejected or of the `Location` value, so none of them is chained into the error raised for a rejected base URL, for an input too long for a URL, or for a redirect status whose `Location` the library cannot use: no exception reachable through `__cause__` and `__context__` is an `httpx.InvalidURL` or an `httpx.HTTPError`. The first two errors also have neither a `__cause__` nor a `__context__`.
  Example: every base URL that AC10 rejects, the 70,000-character buyer and `ocid` of AC10, and the six malformed `Location` cases of AC5 (Revisions 2 and 3) for both operations -> walking the chain finds no such exception, and for the base URLs and the too-long inputs `__cause__` and `__context__` are `None`. An adapter that raises any of these errors `from` the library's exception, or inside the `except` block that caught it, fails this check.
- **AC9** Pacing uses the observed `X-RateLimit-Remaining` header as its only source signal, as advice: the window and key are unknown (Series § Rate limiting). Before each request after the first, the adapter waits through an injected sleeper until a minimum interval has passed since the previous attempt ended. It waits a longer cool-down instead when the previous response had status `429` or a `Remaining` value below a threshold. `X-RateLimit-Limit`, `Retry-After` and any reset header are not used. Defaults (**project decision, not observed**, all configurable): minimum interval 5 s, threshold 20 (borrowed from the stop rule of the observation series, not a source fact), cool-down 60 s (the series only showed a refill within 29 minutes). Tests use an injected monotonic clock and sleeper, so they never sleep.
  Revision 2 (**project decision**, so that pacing protects the source however a call ends): every attempt that was handed to the HTTP client counts, whatever ends it: a result, a source error, or an exception that propagates unchanged (AC15), `KeyboardInterrupt` included. The decision between cool-down and minimum interval reads the status and headers whenever they arrived, whether or not the body was read completely and whatever the status, one outside 100 to 599 included. An attempt that received no status and headers needs only the minimum interval.
  Example (fake clock, defaults): two `200`s with `Remaining: 47`, the second call 2 s after the first ended -> one sleep of 3 s. `Remaining: 19`, then a call 2 s later -> one sleep of 58 s. `Remaining: 20` -> 3 s. A synthetic `429` with no rate-limit header and `Retry-After: 1` -> 58 s. A missing or non-numeric `Remaining` -> 3 s. Repeated `Remaining` values `30` and `5` -> 58 s (the lowest counts). A call 10 s after a `200` -> no sleep. The first call -> no sleep. Revision 2: a `KeyboardInterrupt`, or a synthetic non-`httpx` exception, raised by the transport before the status, then a call 2 s later -> 3 s. A `429`, or a `200` with `Remaining: 5`, whose body read is interrupted by `KeyboardInterrupt` -> 58 s. A synthetic status `600` with `Remaining: 5` -> 58 s; status `600` with no rate-limit header -> 3 s.
  Revision 3 (the audit's finding F-1 and reservation R-3). A valid `Remaining` value is one or more ASCII digits once surrounding spaces and horizontal tabs are removed (the optional whitespace of RFC 9110 § 5.6.3). Any other character, before, inside or after the digits, makes the value invalid, and it is ignored; this includes a non-breaking space (byte `0xA0`) and a superscript digit (byte `0xB2`), which HTTP allows in a field value. A valid value is the decimal number its digits write, leading zeros included, however many digits it has, and it is compared exactly with the threshold, for any threshold the constructor accepts. It is never ignored because the interpreter would refuse to convert that many digits (more than 4,300 by default), and the result does not depend on that interpreter setting.
  Example (fake clock, defaults, next call 2 s later): `Remaining` of 4,999 `0` followed by `5` -> 58 s; 4,300 `0` followed by `5` (4,301 digits) -> 58 s; 4,299 `0` followed by `5` -> 58 s; 5,000 `0` followed by `20` -> 3 s; 5,000 `9` -> 3 s; `low_remaining_threshold` 10**5000 and a `Remaining` of 4,400 `9` -> 58 s; byte `0xA0` then `5` -> 3 s; byte `0xB2` -> 3 s; a tab, `19` and a tab -> 58 s. A `SystemExit` raised by the transport before the status -> 3 s; a `SystemExit` raised while reading a `429` body -> 58 s.
- **AC10** Request discipline. Every request sets explicit timeouts: connect, write and pool 10 s and read 30 s by default (**project decision, not observed**, configurable). The read default clears the 12.01 s observed for a whole request (Series table), while the `httpx` default is 5 s. Every request asks for an uncompressed body (`Accept-Encoding: identity`, **project decision**). Invalid input raises `ValueError` before any request and before any wait.
  Revision 2 (**project decisions**). The base URL is checked completely at construction, so that no call can fail on it later and no credential can reach a request, the evidence or a log line: it must carry no user information (nothing before an `@` in the authority, not even an empty one, because the library would turn it into an `Authorization` header and keep it in the URL as sent, and ADR 0003 and `AGENTS.md` exclude authentication and secrets); its host must be non-empty; a port, when a `:` follows the host, must be 1 to 5 ASCII digits with a value from 1 to 65535; and the HTTP library must accept the whole URL. A rejected base URL raises `ValueError` whose message, `__cause__` and `__context__` do not contain the base URL. A buyer name or `ocid` that makes the request URL longer than the HTTP library accepts is invalid input too: `ValueError` before any request or wait, with no change to pacing. A call after `close()` (or after leaving the `with` block) raises `RuntimeError` before any request or wait, with no change to pacing.
  Example: the handler sees timeouts `connect` 10, `read` 30, `write` 10, `pool` 10 and `Accept-Encoding: identity`. Page `0`, year `True`, an empty buyer, an empty `ocid`, or `min_interval=-1` at construction -> `ValueError`, the handler is never called, and the sleeper is never called. Revision 2: `base_url` `https://synthetic-user:synthetic-secret@source.invalid/PLATAFORMA`, `https://synthetic-user@source.invalid/PLATAFORMA` or `https://@source.invalid/PLATAFORMA` -> `ValueError`, and neither `synthetic-user` nor `synthetic-secret` appears in its message or chain. `https://:8443/PLATAFORMA`, `https://source.invalid:abc/PLATAFORMA`, `https://source.invalid:/PLATAFORMA`, port `0`, `65536`, `99999`, `+8443` or the Arabic-Indic digit `٣`, `https://999.1.1.1/PLATAFORMA`, or a newline inside the path -> `ValueError` at construction. Ports `1`, `8443` and `65535` are accepted. A buyer or `ocid` of 70,000 `a` characters -> `ValueError`, the handler and the sleeper are not called, and the next valid call waits as if the rejected call had not happened. A call after `close()` -> `RuntimeError`, the handler and the sleeper are not called.
  Revision 3 (**project decisions**; the audit's finding F-2 and the family check in `execution-plan.md` § Family check). Revision 2's guarantee, "no call can fail on it later", is replaced by a precise one, and the construction rules are extended so that the code delivers it. The base URL is checked at construction so that a call can fail because of it only as a source outcome: when its host does not resolve or cannot be reached, each call raises the transport error of AC6, as for any network failure. A request URL too long for the HTTP library can come only from that call's own input. To deliver this, construction also raises `ValueError` (with no URL text in its message or chain, as above) when:
  - the host, in the form the HTTP library hands to name resolution and TLS (its ASCII form, IDNA-encoded for a non-ASCII host; an IPv6 literal without its brackets), has an empty label other than a single final one after a trailing dot, or a label longer than 63 characters, or is longer than 253 characters without that trailing dot. RFC 1035 § 2.3.4 sets these limits. Python's `idna` codec, which name resolution and TLS apply to the host, raises an unmapped `UnicodeEncodeError` for the first two. The library already rejects the third for a non-ASCII host;
  - the HTTP library cannot decode the host back from IDNA (a first label starting with `xn--` that is not a valid IDNA A-label). The library decodes it while it builds every request and raised an unmapped `idna.IDNAError`;
  - the host is an IPv6 literal with a zone identifier (a `%` inside the brackets). A zone names a network interface of the local machine (RFC 6874), so it has no meaning for a remote portal, and its text would reach name resolution and TLS unchanged;
  - the HTTP library would reject the request URL that the shortest valid input of either operation gives (year `1`, page `1` and buyer `a`; `ocid` `a`), so the base URL leaves room for the fixed path and query.
  Construction also raises `ValueError` when `connect_timeout`, `read_timeout`, `min_interval` or `cooldown` is not an `int` or a `float` (a `bool` is rejected), is not finite, or is above 86,400 s (one day; **project decision**). A `NaN` interval silently switched pacing off. An infinite or very large value made every call fail with an unmapped error from the socket layer (on Windows a socket accepts at most 2,147,483.647 s) or from `time.sleep`. One day is far above every value this project uses and within every limit found.
  Input. A year, page, buyer or `ocid` that makes the request URL longer than the HTTP library accepts is invalid input, and so are a year or page with more digits than the interpreter writes as text (4,300 by default) and a buyer or `ocid` that cannot be encoded as UTF-8 (a lone surrogate). Each raises `ValueError` before any request and before any wait, with no change to pacing.
  Example (Revision 3). Rejected at construction: `https://` + 64 `a` + `.invalid/PLATAFORMA`; `https://a..invalid/PLATAFORMA`; `https://.source.invalid/PLATAFORMA`; `https://source.invalid../PLATAFORMA`; a host of 254 characters (labels of 63, 63, 63 and 62); `https://xn--.invalid/PLATAFORMA`; `https://xn--ls8h.invalid/PLATAFORMA`; `https://[fe80::1%25eth0]/PLATAFORMA`; `https://[fe80::1%eth0]/PLATAFORMA`; `https://source.invalid/` followed by 65,500 `p`; `connect_timeout` `nan`, `inf`, 86,401 or `True`; `read_timeout` `nan` or `1e10`; `min_interval` `nan`, `inf` or 86,401; `cooldown` `nan`, `inf` or `"60"`. Accepted: a 63-character label; a host of exactly 253 characters, with or without a trailing dot; `https://source.invalid./PLATAFORMA`; `https://[::1]:8443/PLATAFORMA`; `https://source.invalid/PLATAFORMÁ` (sent percent-encoded, and the raw response holds the URL as sent); `https://source.invalid/P%zz`; all four values at 86,400; timeouts of 0.5. Calls: year or page 10**5000, or a buyer or `ocid` of `"\ud800"` -> `ValueError`, and the handler and the sleeper are not called. With a base URL of 65,023 characters, which construction accepts, a search with a year of 4,000 digits -> `ValueError` before any request or wait.

- **AC15** (failure, Revision 2) The set of outcomes is closed, so F4 knows exactly what to catch. A call returns a result or raises one of the source errors (AC5 to AC7), `ValueError` for invalid input or construction (AC10), or `RuntimeError` for a call after `close()` (AC10). Nothing the source sends, and nothing the HTTP library reports about it, escapes in any other form. Every other exception is not a source outcome and propagates unchanged, never wrapped: `KeyboardInterrupt`, `SystemExit`, and any exception raised by an injected transport or by the injected `now`, `monotonic` or `sleep` that is not one of the HTTP library's own errors (**project decision**: a defect of a test double or of the caller must stay visible).
  Example: a transport that raises a synthetic non-`httpx` exception before the status, or from the body stream after one chunk -> that same exception object propagates, it is not a source error, and the attempt still counts for pacing (AC9). The cases of AC5, AC6 and AC10 marked Revision 2 (malformed `Location`, invalid status, user information, port and host, URL too long, call after `close()`) each end in the type named there, never in `httpx.InvalidURL`, an untyped `ValueError` or another library exception.
  Revision 3. The cases of AC3, AC5, AC7, AC9 and AC10 marked Revision 3 belong to the closed set in the same way: an undecodable `Location` host, a `Set-Cookie` value, a body with non-standard constants, huge integers or deep nesting, a long `Remaining` value, and the new base URL, option and input rules each end in the outcome named there. `SystemExit` is tested next to `KeyboardInterrupt`. Exhausting the process's memory (`MemoryError`, for example on a body larger than the memory available) is not a source outcome either: it propagates unchanged and the attempt counts for pacing, because no limit on body size was observed or is set (**project decision**, see Open questions).
  Example: a transport that raises `SystemExit` before the status, or from the body stream after one chunk -> that same object propagates, for both operations, and is not a source error.

## Scope
**In**
- `domain`: the raw response value (one response as received) and the closed set of source errors, sharing one base, each carrying the response when one was received.
- `application`: the source port (a search page by year, buyer name and page; a record by `ocid`) and its two result types.

## Constraints
- Single source of truth for source behavior: `docs/sources/sercop-observations.md`. Every source statement in these specs cites one of its sections or is labelled a project decision. These are not assumed anywhere: the meaning of `local=1`; the rate-limit window and key; whether a `429` carries `Retry-After` and what its body is; any `5xx` body; the answer for an unknown `ocid`; whether `api/record` structure varies between records; filtering by RUC or `buyerId`. Every requirement that touches one of them (AC5, AC6, AC7, AC9) holds whatever the source does.
- ADR 0002 and ADR 0005 are binding. Every response received, whatever its status and whether or not it is complete, must be able to reach the raw store unchanged. F1's port and adapter do not change. Revision 2 reads "response" as a valid HTTP response: a message whose status is outside 100 to 599 is invalid under RFC 9110 § 15, F1 rejects it (RE-11), and F2 reports it as a transport error without a response (AC6). This reading needs the human's approval (Open questions). A malformed `Location` header no longer costs the response (AC5).
- ADR 0006 (`Accepted` by the human at gate 1 on 2026-10-10): `httpx` with a synchronous `httpx.Client`, imported only in `infrastructure`; transport injected; tests use `httpx.MockTransport` with no extra mocking package; explicit timeouts; retries, backoff and pacing decided here, not delegated to the library. These specs treat its decision as binding and do not change its status.
- Layer boundaries from `AGENTS.md` and `docs/architecture.md`; strict `mypy` in `domain` (ADR 0004).
- No new infrastructure, framework, service or CLI command. `httpx` is the only new dependency (approved by the human); its transitive packages come with it in `uv.lock`.
- Tests, fixtures and docs hold no secrets, cookies, real raw responses or complete datasets (`AGENTS.md`). URLs in tests use `.invalid`; cookie and error bodies are synthetic and labelled so.
- Responses may be sensitive: no body bytes or header values in messages, `repr` or logs (same discipline as F1, RE-7 and Invariant 5).
- No credential may enter a request, the evidence or a log line through the base URL (`AGENTS.md`; ADR 0003). With user information in the base URL, `httpx` 0.28.1 sends an `Authorization: Basic` header, keeps the user information in `str(request.url)` (so in `RawResponse.url`) and prints it in its `INFO` record. Construction rejects it (AC10).
- Current-truth notes (`harny-sync` lookup):
  - `project-toolchain` PT-11 says the system keeps `[project] dependencies` empty, and its Invariant 4 says it stays empty "until a runtime dependency is explicitly approved". F2 adds `httpx` there, with the human's approval, so at archive PT-11 is modified and Invariant 4 is fulfilled, not broken. The `dev` group does not change.
  - PT-3 (layer import rules) is kept and extended by one check: only `infrastructure` may import `httpx`.

Revision 2 keeps the raw response inside the RE-11 range, so every response F2 carries can be stored, and reports an invalid status without a response (AC6).

## Open questions
The Revision 3 questions below were closed on 2026-10-10: the human approved Revision 3 and accepted the recommendation on each. Each has the architect's recommendation. Approving Revision 3 also accepts the architect's choices on the audit's two blocking findings, recorded with their reasons in `tasks.md` § Finding responses: F-1, keep the AC9 rule and compare long `Remaining` values exactly; F-2, extend the construction rules and state the guarantee precisely (AC10).
- Revision 3, AC15: do you accept that a body larger than the memory available ends in an unchanged `MemoryError`, with no body-size limit in F2? The alternative is a configurable maximum body size that ends the read with a transport error carrying the bytes read so far. Recommendation: accept. No body above a few kilobytes was observed (the largest fixture is 1,869 bytes), any limit would be invented, the evidence could not be stored anyway once memory is exhausted, and F4 can add a limit if a large body is ever observed.
- Revision 3, AC10: do you accept the upper bound of 86,400 s (one day) for both timeouts, `min_interval` and `cooldown`? The alternative is "finite" only, which still lets a value such as `1e10` make every call fail with an unmapped `OverflowError` on Windows. Recommendation: accept. The defaults are 5 to 60 s, the largest socket timeout Windows accepts is 2,147,483.647 s, and the bound is checked once, at construction.
- Revision 3, AC7: do you accept that `NaN`, `Infinity` and `-Infinity` make a `200` body unusable, that a body with an integer of more than 4,300 digits or nesting too deep to parse is unusable, and that the last value of a repeated name counts? The alternatives are to accept the non-standard constants as Python does, to parse integers of any length with a custom parser, or to reject repeated names. Recommendation: accept. RFC 8259 does not allow the constants, none of these bodies was observed, the complete response is kept as evidence in every case, and F5 can read it again with other rules.
- Revision 2, AC6 (closed: the human accepted it on 2026-10-10, recommendation followed): do you accept that a message whose status is outside 100 to 599 raises a transport error without its bytes, so this one case is not kept as evidence? The alternative is to widen the range of the raw response and of F1's `Observation` (RE-11) in a separate feature, so that such a message can be stored, and F1 must not change in F2. Recommendation: accept. No such status was ever observed; RFC 9110 calls it invalid; `h11` already reports a status below 100 as a protocol error, which F2 maps to the same transport error without a response; and the message keeps the status number for F4 to record.
- Revision 1 questions are closed: at gate 1 the human accepted the echoed-`page` check (AC7) and the pacing defaults (AC9).

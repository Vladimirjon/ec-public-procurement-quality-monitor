## Outcome
The system can keep the audit trail of ingestion in PostgreSQL, following
[ADR 0007](../../docs/adr/0007-postgresql-persistence.md): each ingestion run
(its scope, start, end and status), each piece of raw evidence by content hash
and size, each observation that ties a response to the run that obtained it,
and an append-only list of audit events per run. The raw bytes stay in the
local store of ADR 0005; PostgreSQL holds identity, metadata and audit only.
The database itself refuses to change or delete evidence, observations and
audit events, and repeating the same write is a no-op while a different write
under an existing identity is an explicit integrity error, never an overwrite.
F3 delivers the schema as numbered SQL migrations, a migration runner owned by
the project, the domain types and errors, a persistence port in `application`,
the `psycopg` adapter in `infrastructure`, integration tests against a real
PostgreSQL 18, and the CI service that runs them. Nothing calls the adapter
yet (no CLI command, no ingestion use case).

## Acceptance criteria
All examples use synthetic data. `sha256(b"abc")` is
`ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad` (written
`<abc>` below) and `sha256(b"")` is
`e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` (`<empty>`).
URLs use the reserved `.invalid` domain. A *throwaway database* is a database
created for one integration test and dropped after it, never the database
named in the developer's `.env` (AC14). "Rejected" means the statement fails
and the table is unchanged. JSON values are written in Python notation, so
`True` is the JSON `true`. The exact names of modules, types, errors, the
port's methods, the JSON comparison, the bookkeeping table and the lock key are
pinned in `execution-plan.md` § Binding constraints.

- **AC1** The migration runner applies every pending file of the migrations directory once, in the lexical order of their names, and records each one in a bookkeeping table (version, file name, SHA-256 of the file's exact bytes, time applied). Running it again applies nothing and changes nothing. It returns the names of the files it applied in that call.
  Example: on an empty throwaway database, applying the repository's `migrations/` -> returns `("0001_initial_schema.sql",)`; the tables `ingestion_run`, `raw_evidence`, `observation` and `audit_event` exist; the bookkeeping table has one row, version `1`, file name `0001_initial_schema.sql`, and the SHA-256 of that file's bytes. A second call -> returns `()` and the bookkeeping rows are unchanged.
- **AC2** (failure) A migration that fails leaves no trace of itself: everything it did is rolled back, it is not recorded as applied, files after it are not attempted, and the files applied before it stay applied. The error names the file and nothing from the database's message. Because the failed file was never applied, it may be corrected and the runner run again.
  Example (synthetic migrations in a temporary directory): `0001_a.sql` creates table `synthetic_a`; `0002_b.sql` creates table `synthetic_b` and then runs `SELECT 1/0`; `0003_c.sql` creates `synthetic_c`. Applying -> `MigrationError` whose message names `0002_b.sql`; `synthetic_a` exists, `synthetic_b` and `synthetic_c` do not, the bookkeeping table holds only version `1`. With `0002_b.sql` corrected, applying again -> returns `("0002_b.sql", "0003_c.sql")`.
- **AC3** (failure) The runner checks the migrations directory and every applied file before it applies anything, and refuses to continue on any mismatch: an applied file whose bytes changed (checksum differs), an applied file that is missing or renamed, a `.sql` file whose name is not `NNNN_description.sql`, two files with the same number, a gap in the numbering, a file that is empty, holds only whitespace, holds U+0000, or is not UTF-8. The error names the file and applies nothing. Name checks happen before any connection is opened.
  Example: after `0001_a.sql` is applied, one byte of it is changed and `0002_b.sql` is added -> `MigrationError` naming `0001_a.sql`, and `synthetic_b` does not exist. Files `0001_a.sql` and `0003_c.sql` (no `0002`), or `0001_a.sql` and `0001_b.sql`, or `1_a.sql` -> `MigrationError` naming the offending file, with no connection attempt.
- **AC4** (failure) Only one migration run works on a database at a time. When another session holds the runner's lock, the runner fails at once with an explicit error and applies and creates nothing; it never waits.
  Example: a separate test connection to an empty throwaway database holds the advisory lock with the pinned key; applying -> `MigrationError` saying another migration run holds the lock; the bookkeeping table does not exist. Once the lock is released, applying succeeds.
- **AC5** The schema enforces the identities and rules of the four tables, so invalid rows are rejected by the database even when written with direct SQL.
  Example (direct SQL on a migrated throwaway database), each rejected: a run with execution id `Synthetic-Exec` or `-x`; a run with status `paused`; a `running` run with a `finished_at`; a `failed` run without one; a run whose `finished_at` is before its `started_at`; a run whose `scope` is a JSON array; a `raw_evidence` row whose hash has 63 characters or uppercase letters, or whose size is `-1`; an observation with sequence `-1`, an empty method or URL, status `99` or `600`, an unknown run, an unknown content hash, `headers` that are not a JSON array, or a header named `SET-COOKIE` (any case); an audit event with an empty `event_type`, an unknown run, a `detail` that is a JSON array, or an explicit `event_id`. A second row with an existing primary key -> rejected. An audit event inserted without `detail` -> stored with `{}`.
- **AC6** The database keeps evidence, observations and audit events append-only, and lets a run change only once, from `running` to `succeeded` or `failed`.
  Example (direct SQL): `UPDATE` or `DELETE` on `raw_evidence`, `observation` or `audit_event`, and `TRUNCATE` on `observation` or `audit_event` -> rejected with SQLSTATE `23000`, rows unchanged. A plain `TRUNCATE` on `raw_evidence` or `ingestion_run`, which other tables reference by foreign key, -> rejected with SQLSTATE `23000` or `0A000` (PostgreSQL's foreign key check may refuse it before the trigger runs), rows unchanged; `TRUNCATE ... CASCADE` on either -> rejected with SQLSTATE `23000`, rows unchanged. On `ingestion_run`: `DELETE` -> rejected; setting `status` `succeeded` with a `finished_at` on a `running` run -> accepted; afterwards, any further `UPDATE` (to `failed`, back to `running`, a new `finished_at`, a new `scope`) -> rejected with SQLSTATE `23000`; changing `execution_id`, `scope` or `started_at` of a `running` run -> rejected.
- **AC7** Runs are started, finished and read through the port, and repeating a write with the same values is safe. Two scopes are the same only when they are the same JSON value: types are compared too, at every depth, so `True` is not `1` and `False` is not `0`; object key order does not matter; list order does.
  Example: `start_run` of `synthetic-exec-001`, scope `{"source": "synthetic", "year": 2025}`, started at `2026-10-09T10:15:00-05:00` -> returns a `running` run; `read_run` -> an equal run. The same `start_run` again (same scope and start instant) -> returns the stored run as it is and changes nothing; with another scope or start time -> `PersistenceIntegrityError`. `finish_run` with `succeeded` at `2026-10-09T10:15:42-05:00` -> a `succeeded` run with that `finished_at`; the identical `finish_run` again -> equal run, no change; `finish_run` with `failed`, or with another time -> `PersistenceIntegrityError`. `finish_run` with status `running`, or with the plain string `"succeeded"` instead of the run status value -> `ValueError` before anything is written. `read_run` or `finish_run` of an id never started -> `PersistenceNotFoundError`. Times read back are the same instants, in UTC.
  Example (JSON types, Revision 2): a run started with scope `{"x": 1}`, then `start_run` with the same id, start time and scope `{"x": True}` -> `PersistenceIntegrityError`. The same with `{"x": [1]}` then `{"x": [True]}`, and with `{"x": {"y": 0}}` then `{"x": {"y": False}}` -> `PersistenceIntegrityError`. A run started with `{"x": [1, {"y": True}]}` and the identical `start_run` repeated -> returns the stored run unchanged; `{"b": 1, "a": 2}` repeated as `{"a": 2, "b": 1}` -> the same run; `{"x": [1, 2]}` repeated as `{"x": [2, 1]}` -> `PersistenceIntegrityError`.
- **AC8** Observations are recorded and read through the port. Each content is one `raw_evidence` row whatever the number of observations; each response obtained is one observation row; the observation's size is read from `raw_evidence`. Repeating the identical observation is a no-op; a different observation under an existing (execution, sequence) is an integrity error, and its transaction is rolled back, so nothing of it is written, not even the new content's row.
  Example: with runs `synthetic-exec-001` and `synthetic-exec-002` started, `record_observation` of the F1 example observation (sequence `1`, `GET https://source.invalid/api/search?year=2025&page=1`, status `200`, headers `Content-Type: application/json`, `X-A: 1`, `X-A: 2`, captured at `2026-10-09T10:15:00-05:00`, content hash `<abc>`, size `3`) for both runs -> one `raw_evidence` row (`<abc>`, `3`) and two observation rows; `read_observation("synthetic-exec-001", 1)` equals the observation given, headers in the same order with the repeat kept; `list_observations("synthetic-exec-001")` returns it alone, in sequence order. The identical call again -> equal observation, row counts unchanged. The same identity with status `500`, another header order, or content `<empty>` size `0` -> `PersistenceIntegrityError`, the stored row unchanged, and no `raw_evidence` row for `<empty>`. An observation for a run never started -> `PersistenceIntegrityError` and no `raw_evidence` row written. `read_observation` of an identity never recorded -> `PersistenceNotFoundError`; `read_observation("../escape", 1)` -> `ValueError`. Text outside ASCII (for example a URL `https://source.invalid/búsqueda?año=2025`, a header value `Adquisición de equipos`, and Spanish keys and values in the run's scope and in an event's detail) is stored and read back unchanged, and repeating those writes is a no-op.
- **AC9** Audit events are appended and listed through the port. The database assigns each event its identity, and events list in the order they were appended. The set of event types is deliberately not defined in F3 (F4 defines the catalogue); F3 requires only a non-empty type and a JSON object as detail. Appending is not idempotent: the same call made twice appends two events (resolved question 8).
  Example: `append_audit_event` for `synthetic-exec-001` with type `synthetic-run-started`, detail `{}`, then type `synthetic-page-stored`, detail `{"page": 1}` -> two events whose `event_id` values increase; `list_audit_events("synthetic-exec-001")` returns them in that order, equal to what was returned (details compared as JSON values, so `{"page": True}` is not equal to `{"page": 1}`). An empty type -> `ValueError` before anything is written; a run never started -> `PersistenceIntegrityError`.
- **AC10** (failure) Input that the domain rules reject, or that PostgreSQL cannot store as given, is rejected with `ValueError` before anything is written. The domain rules: an execution id outside the F1 pattern; a time without a UTC offset; a `finished_at` before `started_at`; a scope or detail that is not a JSON object made only of `None`, `bool`, `int`, `str`, `list` and `dict` with `str` keys. A `float` is rejected anywhere in scope or detail (**project decision**: `jsonb` stores numbers as exact decimals, so some floats do not read back equal, for example `1e23` reads back as the integer `10**23`; NaN and infinities are not JSON at all). PostgreSQL limits: text holding U+0000 or a lone surrogate anywhere (method, URL, header names and values, event type, keys and strings inside scope or detail); a sequence above 2,147,483,647; a size above 9,223,372,036,854,775,807. Writing limit: an integer in scope or detail with more than 4300 decimal digits (the interpreter's default limit for writing an integer as text) cannot be written as JSON text.
  Example: a scope `{"year": 2025.0}`, `{"year": float("nan")}`, `{1: "x"}`, `{"pages": (1, 2)}` or `{"pages": {1, 2}}`; a naive `started_at`; `finish_run` with a `finished_at` one second before the stored `started_at`; an observation whose URL contains `"\x00"` or whose header value is `"\ud800"`; an event detail `{"note": "a\x00b"}`; sequence `2**31`; a scope or an event detail `{"n": 10**5000}` -> `ValueError`, and the table row counts are unchanged.
- **AC11** (failure) Connection problems are typed errors, and each operation's transaction is atomic: it is applied completely or not at all, never in part. A database that cannot be reached, or that refuses the credentials, raises `PersistenceConnectionError` when the adapter is built. A connection lost during an operation raises `PersistenceConnectionError`, and the adapter does not reconnect: later calls raise the same error. A call after `close()` raises `RuntimeError`. `PersistenceConnectionError` is **not** a guarantee that nothing was written. A connection lost before the operation's statements are sent, or while its transaction is still open, leaves nothing written. A connection lost while the commit is in flight leaves the outcome **unknown**: the transaction may have committed in full or not at all. A caller (F4) must therefore not read the error as proof that a retry cannot duplicate. `start_run`, `finish_run` and `record_observation` are safe to repeat with the same values: a committed first attempt makes the repeat a no-op. `append_audit_event` is not safe to repeat: it may append the event twice (resolved question 8).
  Example (deterministic cases, tested): settings pointing at a closed local port, or at the throwaway database with the password `synthetic-wrong-password` -> `PersistenceConnectionError`. The adapter's server session is terminated from a test connection (`pg_terminate_backend`) before `record_observation` is called -> `PersistenceConnectionError`, no row written; the next `read_run` -> `PersistenceConnectionError`. A test connection holds `LOCK TABLE observation IN ACCESS EXCLUSIVE MODE`; `record_observation` runs in a worker thread, inserts its `raw_evidence` row and waits on the lock (seen in `pg_stat_activity`); its server session is then terminated -> `PersistenceConnectionError`, and once the lock is released no `raw_evidence` row and no observation from that call exist. The AC8 observation for a run never started -> no `raw_evidence` row remains.
  The commit-in-flight case is documented, not tested: making it deterministic needs a proxy that drops the server's reply to `COMMIT` after the server has received it, which means parsing the wire protocol in a test. That is out of proportion for F3. The safety of a repeat is shown instead by the idempotency tests of AC7 and AC8.
- **AC12** (failure) Nothing leaks secrets or stored content. Error messages, `str()`, `repr()`, `args` and formatted tracebacks of the errors F3 raises contain no password, connection setting, SQL parameter or stored value (header values, URLs, scope, detail); they name the operation and, where useful, an identity (execution id, sequence, content hash, migration file name). No exception from the database driver is reachable through `__cause__` or `__context__`. The settings object never shows its password in `repr()` or `str()`. The adapter and the runner write no log records of their own.
  Example: settings with password `synthetic-password-marker` and a wrong port -> `PersistenceConnectionError` in which the marker does not appear (message, `repr`, `args`, `traceback.format_exception`), and `repr(settings)` does not contain it. An AC8 conflict whose stored URL holds `synthetic-url-marker` -> `PersistenceIntegrityError` naming execution and sequence, with no marker and no `psycopg` exception in its chain. The database's own error text for a rejected row quotes the row ("Failing row contains ..."), which is why none of it may pass through.
- **AC13** The layers keep their boundaries. The run, audit event, run status, the JSON comparison and the persistence errors live in `domain` (standard library only, strict `mypy`); the persistence port lives in `application` (standard library and `domain` only); the settings, the runner and the `psycopg` adapter live in `infrastructure`, the only layer that imports `psycopg`. The adapter satisfies the port without the port knowing it.
  Example: `uv run pytest tests/unit -q -k layer` -> passes, including a new check that no module outside `infrastructure` imports `psycopg` in any form; `uv run mypy .` -> exit 0, including an integration test that assigns the adapter to a variable typed as the port (`mypy` checks it whether or not a database is reachable).
- **AC14** Tests run in two tiers and never harm the developer's data. Unit tests need no database and open no socket. Integration tests run against a real PostgreSQL 18. **Each integration test runs in its own throwaway database**, created for that test with the configured user and dropped when the test ends; no two tests share a database. Tests of the migration runner start from an empty database (copied from PostgreSQL's `template0`). Every other integration test starts from a copy of a migrated template database, which the session creates once, uses only as a source for copies, and drops at the end. The template is a speed device, never a place where a test runs. No test creates, changes or drops objects in the configured database. When the connection settings are absent or the server cannot be reached, integration tests are skipped with a reason that says how to run them, except when the environment variable `CI` is `true`, where they fail instead.
  Example: with Docker stopped, `uv run pytest tests/integration -q -rs` -> every integration test skipped with that reason, exit 0; the same with `CI=true` -> failures, non-zero exit. With the Compose database up, `uv run --env-file .env pytest tests/integration -q` -> all pass. Afterwards no database whose name starts with the throwaway prefix remains (the template included), and the configured database holds no object created by the tests.
- **AC15** CI runs the integration tests against PostgreSQL 18 on every pull request and push to `main`, and none is skipped there.
  Example: the `Tests` workflow's `tests` job starts a `postgres:18` service container; its `Run tests` log shows the unit and integration tests passed with `0 skipped` for `tests/integration`, and the coverage table includes the adapter and runner modules.
- **AC16** (compatibility) Everything that worked keeps working, and the only new dependency is the approved one.
  Example: the 961 existing tests still pass inside `uv run pytest`; `uv run ruff check .`, `uv run ruff format --check .` and `uv run mypy .` exit 0; `uv run node .sdd/doctor/run-doctor.mjs` reports `0 warned, 0 failed`; `uv run ec-procurement-quality --version` prints `ec-procurement-quality 0.1.0`; `git diff main -- pyproject.toml` adds only the `psycopg` entry to `[project] dependencies` and the `integration` marker to the pytest configuration; `uv sync --locked` and `uv lock --check` exit 0; F1 and F2 modules, `compose.yaml` and `.env.example` are unchanged; `git ls-files .env` prints nothing; `git diff --check` is clean.
- **AC17** (documentation) The documentation says what exists.
  Example: `README.md` § Technologies names the migrations, the runner and the `psycopg` adapter (library only, nothing calls it), and § Development commands shows how to run the integration tests; `AGENTS.md` § Current commands lists that command; `docs/architecture.md` § Infrastructure boundary says the schema and runner contract exist and § Open questions still lists the audit event catalogue as open; `CHANGELOG.md` § Unreleased lists the feature, the `psycopg` dependency, and the known limitations (unknown outcome after a connection lost during a commit; audit events not idempotent; triggers do not bind a superuser).

## Scope
**In**
- `migrations/0001_initial_schema.sql`: the four tables, their keys and constraints, the append-only triggers and the run-transition trigger (AC5, AC6). The executor writes it and the human reviews it line by line (resolved question 6).
- `domain`: the run status, the ingestion run, the audit event, the JSON value rule and the JSON comparison for scope and detail, and the persistence errors.
- `application`: the persistence port, with operations to start, finish and read a run, record, read and list observations, and append and list audit events.
- `infrastructure`: the connection settings value, the migration runner (library function), and the `psycopg` adapter implementing the port.
- The `psycopg[binary]>=3.3.6` runtime dependency (approved by the human on 2026-10-13).
- Unit tests under `tests/unit/` and integration tests under `tests/integration/`, the `integration` pytest marker, and a layer test for `psycopg`.
- A `postgres:18` service in the `tests` job of `.github/workflows/tests.yml` and the job environment it needs.
- Documentation updates for AC17.

**Out**
- Any CLI command, including a `migrate` command; how F4 applies migrations before an ingestion (resolved question 1).
- The ingestion use case, generating execution ids and sequences, resuming runs, and marking interrupted runs as failed (F4).
- The catalogue of audit event types and the contents of `scope` (F4). F3 requires only a non-empty type and JSON objects; this is deliberate, not a gap (`docs/architecture.md` § Open questions).
- An idempotency key for audit events (resolved question 8).
- A test of the commit-in-flight connection loss (AC11: documented, not tested).
- Raw bytes in PostgreSQL, checking that an object exists in the local store, and keeping the local store and PostgreSQL consistent after a crash between the two writes (F4; ADR 0005 and ADR 0007).
- Requiring a run to be `running` to receive observations or events (F4 decides; recording them after the run finished is not prevented in F3).
- Reading observations by content hash and any lineage query (F5, F6); normalized procurement tables (F5) and quality tables (F6).
- Retries, reconnection, connection pooling, concurrent writers, async access (ADR 0007).
- A least-privilege database role, and protection against a superuser who disables triggers or edits the bookkeeping table (Risks).
- Downgrade migrations (ADR 0007: forward-only); shipping `migrations/` inside a built wheel (owned by the release work, D-13).
- Changes to `compose.yaml`, `.env.example`, the F1 store, the F2 adapter, `.github/dependabot.yml`, ADR 0006 and ADR 0007. The Dependabot correction is a separate change made by the human's session (resolved question 10).

## Constraints
- ADR 0007 is binding: `psycopg` 3 synchronous API with explicit, parameterized SQL and no ORM; only `infrastructure` imports it; ports in `application`; no `psycopg` type or exception crosses into `domain` or `application`; numbered files `migrations/NNNN_description.sql`, forward-only, an applied file is never edited; a runner owned by the project in `infrastructure` that applies each pending file once and in order and records it in the database; PostgreSQL 18 through Docker Compose. ADR 0007 leaves the schema, the `psycopg` variant and the runner contract to this spec; they are in `execution-plan.md`.
- ADR 0002 and ADR 0005: raw bytes stay in the local store; PostgreSQL holds identity, metadata and audit. Evidence is append-only and never silently replaced; the same response obtained again is one more observation, not another copy; `Set-Cookie` is never persisted.
- The four tables and their columns are the human's decisions of 2026-10-13 (`ingestion_run`, `raw_evidence`, `observation`, `audit_event`; the plan's Day 16 listed three). The additions made by this spec were accepted by the human on 2026-10-13 (resolved question 9).
- Layer boundaries from `AGENTS.md`, `docs/architecture.md` and ADR 0001; strict `mypy` in `domain` (ADR 0004).
- `AGENTS.md`: the `psycopg[binary]>=3.3.6` dependency was approved by the human on 2026-10-13 (resolved question 2); no other dependency is added. No secrets, credentials, connection strings with passwords or `.env` contents in code, logs, error messages, tests, specs or docs. `.env` is never read, printed or committed by any role.
- Who writes what (resolved question 6): the executor writes `migrations/0001_initial_schema.sql` from the schema pinned in `execution-plan.md`, and the human reviews it line by line at the executor's hand-off, with each constraint and trigger explained. This replaces "escribe tú las primeras migraciones SQL" of `docs/learning/plan.md` Day 17.
- Tests, fixtures and docs hold no real SERCOP records or raw responses; data is synthetic and URLs use `.invalid`.
- PostgreSQL features relied on were checked on the local PostgreSQL 18.6 on 2026-10-13 (`execution-plan.md` § Guidance consulted): check constraints, `jsonb_path_exists` with `like_regex ... flag "i"`, row and statement triggers raising SQLSTATE `23000`, `GENERATED ALWAYS AS IDENTITY`, `ON CONFLICT DO NOTHING RETURNING`, transactional DDL, session advisory locks, the rejection of `\u0000` and lone surrogates in `jsonb`, and `CREATE DATABASE ... TEMPLATE` refusing a template that another session is connected to.
- Current-truth notes (`harny-sync` lookup): `project-toolchain` PT-3 says only `infrastructure` imports `httpx`; F3 adds the same rule for `psycopg` with its own layer test. PT-11 and Invariant 4 say `httpx` is the only runtime dependency; F3 adds `psycopg` with the human's approval, which Invariant 4 allows. PT-10 says the `tests` job runs the unit tests; F3 adds the PostgreSQL service and the integration tests to it. PT-6 counts 961 tests; the count grows. `raw-evidence` (RE-1 to RE-12) and `source-access` (SA-1 to SA-13) are not changed: F3 reuses `Observation`, `ContentHash`, `validate_execution_id` and `validate_sequence` as they are. `cli` is not changed. The README sentence "the application does not use the database yet" stays true in substance (nothing calls the adapter) and is reworded for AC17.

## Open questions
None open. All ten were resolved by the human at gate 1 on 2026-10-13. The details are in `execution-plan.md` § Proposed approach.
1. **Runner contract and invocation.** Accepted as recommended on 2026-10-13: the bookkeeping table is created by the runner; every applied file's checksum is checked before anything runs; one transaction per file, including its bookkeeping row; a session advisory lock taken with a non-waiting try that fails at once; contiguous numbering from `0001`; `migrations/` at the repository root, passed to the runner as a path; a library function only, with no CLI command in F3.
2. **The `psycopg[binary]>=3.3.6` dependency.** Approved on 2026-10-13. Lockfile impact measured in a scratch copy: 22 to 25 packages, adding `psycopg` 3.3.6, `psycopg-binary` 3.3.6 and `tzdata` 2026.5 (Windows-only marker). Task O1 may proceed once this revision is approved.
3. **Connection settings.** Accepted as recommended on 2026-10-13:
   - a settings value in `infrastructure`, built by the caller, passed to `psycopg` as separate keyword arguments and never as a connection string;
   - no code under `src/` reads the environment or `.env` in F3;
   - the tests read the five `POSTGRES_*` variables, loaded with `uv run --env-file .env`.
4. **Integration tests without a database.** Accepted as recommended on 2026-10-13: they are skipped with a reason locally and fail when `CI` is `true` (AC14).
5. **CI in F3.** Accepted as recommended on 2026-10-13: the `postgres:18` service goes into the existing `tests` job. At archive this modifies `project-toolchain` PT-3, PT-6, PT-10 and PT-11.
6. **Who writes `0001_initial_schema.sql`.** Decided on 2026-10-13: option B, the executor. The human reviews it line by line at the executor's hand-off, and each constraint and trigger is explained to the human. The human does not write it by hand, which replaces the plan's Day 17 task.
7. **Times keep their instant, not their UTC offset.** Accepted as recommended on 2026-10-13.
8. **Audit events have no idempotency key.** Accepted as recommended on 2026-10-13. A repeat after an unknown commit outcome may duplicate an event (AC9, AC11); F4 decides when it defines the event catalogue.
